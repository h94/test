# 系統健康檢查

## 1. 場景目的

提供一個不需驗證的 HTTP Endpoint，供負載平衡器、監控系統或 Kubernetes 的 Liveness Probe 呼叫，以確認服務處於存活狀態。

---

## 2. 入口 API

| Method | Path | 說明 |
|---|---|---|
| GET | `/api/heart` | 不需驗證，回傳服務當前存活狀態 |

---

## 3. 流程總覽

1. 接收 GET 請求
2. 直接回傳代表服務正常運行的 HTTP 200 狀態碼（可能附帶簡單的訊息本體）

---

## 4. 程式流程

| 順序 | Layer | Class / Method | 動作 |
|---|---|---|---|
| 1 | Controller | --- | 接收 GET 請求 |
| 2 | Controller | --- | 回傳 HTTP 200 OK |

> **需人工確認**：由於無具體原始程式碼，無法確定它可能包含 `HeartController` 的哪個方法，也無法得知其回傳內容（可能是 "OK" 或當前時間等簡易資訊）。

---

## 5. DB / Cache / Queue 使用

此場景未使用任何 DB、Redis 或 Queue。

> **需人工確認**：一個完整的 Health Check 實作有時會包含對 DB 或 Redis 的連線測試。根據現有資料，API 僅確認服務存活，**推測**不包含對外部資源的深層連線檢查。

---

## 6. 重要規則

- **權限限制**：此 API 端點不需驗證，任何人都可以呼叫。

---

## 7. 錯誤情境

此端點一般不會進入錯誤流程。服務無法回應時，呼叫方會收到連線逾時或被拒絕。

---

## 8. 測試重點

| Test ID | 類型 | 情境 | 預期結果 |
|---|---|---|---|
| T01 | API Test | 對 `/api/heart` 發送 GET 請求 | 回傳 HTTP 200 OK |
| T02 | Flow Test | 服務部署後，監控系統探測 `/api/heart` 是否回應 | 監控儀表板應顯示服務為健康狀態 (UP) |

---

## 9. 高風險區域

- **無**：此為唯讀、不操作任何資料的端點。
- **注意**：若此端點被用來探測服務是否「就緒 (Ready)」而非僅「存活 (Alive)」，則實作上可能需要檢查後端依賴（如 DB），但此文件僅分析存活檢查。

---

## 10. 常見錯誤

- **無顯著常見錯誤**。
- **依賴混淆**：新人或 AI 可能誤將此 API 用於驗證 DB/Cache 連線狀態，若未實作該檢查則會掩蓋真正的依賴問題。
