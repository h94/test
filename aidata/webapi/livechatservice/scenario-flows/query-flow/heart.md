# 服務心跳

## 1. 場景目的
提供一個對外端點，回傳服務當前時間，供監控或外部服務確認服務存活和時間同步。

---

## 2. 入口 API

| Method | Path | 說明 |
|---|---|---|
| GET | /api/heart | 無參數，直接返回服務器時間 |

來源：OpenAPI `paths./api/heart.get`，summary「看時間」(健康檢查用途)。

---

## 3. 流程總覽

1. 客戶端呼叫 `GET /api/heart`。
2. 服務端無需任何前置驗證（無 token、無參數）。
3. 內部取得系統時間（可能是 `DateTime.UtcNow` 或本地時間，需人工確認）。
4. 以字串格式回傳時間，HTTP 200。

- ❗ 無 DB、Redis、Kafka、文件儲存等操作；為最簡易的唯讀端點。

## 6. 重要規則

- **無權限限制**：不需任何驗證，完全公開。
- **無狀態性**：純讀取，冪等且無副作用。
- **時間來源**：直接使用作業系統時間，注意時區設定（Dockerfile `TZ=Asia/Taipei`，容器內時間為台北時間，回傳可能為 UTC 或本地時間，依程式碼決定 — 需人工確認）。
- **回應格式**：根據 OpenAPI，可回應 `text/plain`、`application/json`、`text/json`，皆為 `string` 型態。格式需與 client 端約定一致，避免解析錯誤。

---

## 7. 錯誤情境

| 情境 | 預期結果 |
|---|---|
| 伺服器正常運作 | HTTP 200，回傳包含當前時間的字串 |
| 伺服器內部異常（如記憶體錯誤） | 可能返回 500，但此端點無複雜邏輯，發生機率極低，**需人工確認**是否有全域錯誤處理 |

- 此端點無輸入參數，故無參數校驗錯誤。
- 無 DB/Cache/Queue 依賴，故無資料層錯誤。

## 10. 常見錯誤

- **格式不一致**：開發或 QA 誤以為回傳固定格式（如 `2025/04/01 12:00:00`），但實際可能回傳 JSON 字串 `"2025-04-01T12:00:00Z"`，導致客戶端解析失敗。
- **時區混淆**：誤認為回傳 UTC，實際程式碼因 Docker `TZ=Asia/Taipei` 而回傳 +08:00 時間，需檢查程式碼確認。
- **誤加驗證**：若後續維護者不小心加入 `[Authorize]`，會導致健康檢查失敗。

### 需人工確認事項

1. **實作類別與方法**：具體位於哪個 Controller，方法名稱是 `Heart()` 還是其他。
2. **時間格式**：回傳的字符串確切格式（例如 `2025-04-01T12:00:00+08:00` 或僅 UNIX 秒）。
3. **時區**：程式碼內使用的是 `DateTime.Now`（受容器 TZ 影響）還是 `DateTime.UtcNow`，這決定了回傳時間的語意。
4. **是否有記錄寫入**：是否有最低程度的 Kafka 日誌寫入（如訪問記錄），依 README 推測「整合 KafkaLogger 記錄服務運作日誌」，**可能會有額外的背景日誌記錄，不影響回應**。
