# 验证Token

## 1. 场景目的

检查给定的令牌（Token）是否有效，即该令牌是否存在于系统中且未过期。供第三方服务集成时进行身份验证或授权校验。

---

## 2. 入口 API

| Method | Path | 说明 |
|---|---|---|
| GET | /api/v1/token/check | 验证Token有效性 |

**查询参数**：`token`（字符串，必填）。

**响应**：返回整数状态码（需确认：1表示有效，0表示无效）。

> Evidence: OpenAPI specification — `/api/v1/token/check`

---

## 3. 流程总览

1. 接收 HTTP GET 请求，携带查询参数 `token`。
2. 检查 `token` 参数是否存在且非空；若缺失，返回错误或无效标识。
3. 通过数据访问层查询存储介质（数据库或缓存）中的 Token 记录。
4. 若记录不存在，判定为无效。
5. 若记录存在，获取其过期时间，并与当前系统时间比较。
6. 若已过期，判定为无效；否则判定为有效。
7. 返回有效性状态码。

> ⚠️ **需人工确认**：具体存储介质（MySQL 或 Redis）及表结构，需查看源代码。

## 6. 重要规则

- **权限限制**：当前接口公开给第三方服务，无额外权限控制，仅依赖 Token 本身。
- **参数要求**：`token` 为字符串，需校验非空，长度或格式可能有限制。
- **信息暴露控制**：验证不应返回 Token 的创建者、创建时间等内部数据。
- **过期判定**：依赖 `expirationtime`，需保持时钟同步；判定标准为 `当前时间 >= 过期时间` 则视为过期。
- **防重放**：当前设计未明确包含，需确认是否需要额外机制。
- **Transaction**：无写操作，无需事务。

> Evidence: API 参数说明来自 OpenAPI；过期时间设定参考 `/api/v1/token/get` 的 `expirationtime` 参数（最小0，最大5天）。

## 7. 错误情境

| 情境 | 预期结果 |
|---|---|
| Token 不存在于数据源 | 返回 0（无效） |
| Token 已过期 | 返回 0（无效） |
| `token` 参数缺失 | 返回 400 或 0（需确认） |
| 数据源连接失败 | 返回 500 或 503，需有错误处理 |
| 传递非法格式 Token | 返回 0 或 400 |

## 9. 高風險区域

- **高風險 API**：`/api/v1/token/check` 是鉴权入口，需保证高性能与高可用。
- **数据一致性**：若同时在 DB 和 Redis 存储，需有缓存失效和更新策略。
- **时间精确性**：过期判断依赖服务器时间，集群时间需同步。
- **安全性**：Token 通过 URL Query String 传递，可能被 Web 日志记录，存在泄露风险。
- **幂等性**：纯读操作，天然幂等。

---

## 10. 常见错误

- 新人对返回值含义不明确，可能误认为 `0` 是成功。
- AI 易假设 Token 存储仅使用 Redis，忽略数据库作为主存储可能。
- 遗忘对 `token` 参数进行空值/格式校验。
- 过期判断时未统一时间单位（秒 vs 毫秒），导致错误比对。
- 测试时只测正常情况，未覆盖数据库异常或并发场景。
