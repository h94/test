# 定期快取清理與服務重啟

## 1. 場景目的
本場景描述 InplayzSubscriptionSystem 的內部定時維護任務，包含定期清理過期商務快取、移除逾時 SignalR 連線，以及每週五下午自動重啟服務以確保長期穩定性。目的在於避免記憶體洩漏、過期資料堆積與連線僵屍，維持系統高可用。

## 3. 流程總覽
⚠️ **需人工確認**：以下流程基於 README 描述推導，具體實作細節待補充。

1. 排程觸發（例如每 5 分鐘或每小時，清理頻率未知）
2. 掃描商務快取，比對訂閱到期時間，移除已過期的快取條目
3. 檢查所有 SignalR 連線，斷開閒置超過閾值的連線並清除連線紀錄
4. 若為週五下午，觸發服務重啟流程（可能透過呼叫外部健康檢查端點或內部自我關閉，需人工確認）
5. 記錄清理日誌

## 6. 重要規則
- **權限限制**：無外部呼叫，全為內部系統程序。
- **不可暴露資料**：清理過程不應輸出快取內容至日誌。
- **TTL 規則**：快取本身的 TTL 可能由寫入時設定，清理為被動掃描雙重保障。
- **重啟時機**：僅限定於每週五下午（Asia/Taipei 時區），不可在其他時間執行，避免影響賽事推送。
- **優雅關閉**：重啟前需確保所有 Kafka consumer 已停止接收新訊息，並完成當前批次處理（需確認實作）。
- **連線逾時閾值**：需定義閒置多久的連線視為逾時（如 30 分鐘無資料傳輸）。

## 7. 錯誤情境
| 情境 | 預期結果 |
|------|----------|
| Redis 連線失敗 | 清理中斷，記錄錯誤，排程下次嘗試 |
| SignalR 連線掃描時 Hub 被外部釋放 | 捕捉異常，跳過該連線，繼續清理 |
| 服務重啟過程中仍有客戶端連線 | 客戶端應實現自動重連機制；服務需經由 Docker Swarm 無縫替換容器 |
| 快取清理誤刪仍有效的 key（如比對邏輯錯誤） | 導致商務驗證重新查詢 DB，增加延遲但非致命 |
| 重啟觸發失敗（如週五未重啟） | 服務繼續運行，可能累積記憶體；監控需告警 |

| Test ID | 類型 | 情境 | 預期結果 |
|---------|------|------|----------|

## 9. 高風險區域
- **高風險 API**：無對外 API，但若重啟透過 `/health` 或 `/signalr` 端點，誤用可能導致非預期重啟。
- **跨服務資料同步**：清理快取可能短暫導致商務驗證穿透到 DB，需確保 DB 查詢效能足夠。
- **Cache consistency**：清理必需精準，不可誤刪未過期資料；雙重確認機制 (TTL + 手動清理) 較安全。
- **重啟流程的 Idempotency**：需確保重啟操作不會重複執行（如用 flag 或排程鎖）。
- **Queue retry**：若重啟時有 Kafka message 未 commit，需確保 consumer 正常關閉並重新加入後不遺失或重複消費。

## 10. 常見錯誤
- **新人容易犯錯**：直接信任快取過期邏輯（如只依賴 TTL），忽略被動清理的必要性；重啟腳本未考慮容器環境，導致服務被殺而非優雅關閉。
- **AI 容易誤解**：以為「自動重啟」僅是內部排程，實際上可能由外部 Docker Swarm scheduler 觸發，AI 生成代碼可能嘗試自我 Process.Kill，違反設計。
- **常見漏檢查項目**：未驗證 Redis 連線狀態直接操作；未 logging 清理數量，導致難以追蹤。
- **常見錯誤流程**：重啟條件未判斷今天是週五且下午時段，導致非預期重啟；逾時連線清理時未檢查連線是否正在傳送資料（只依據最後訊號時間）。
