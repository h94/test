## 視覺設計（DESIGN.md）

若 repo 根目錄存在 `./DESIGN.md`（通常由 `@repo-init` 自 `aidata/templates/design-md/` 複製），編輯 UI **外觀**（色彩、字體、間距、陰影、圓角）前**必讀**。

與本章衝突時：
- **頁面結構、layout、Vuetify 元件用法、API 串接** → 以 `.rules.md` 為準
- **視覺語言、配色、字級階層** → 以 `DESIGN.md` 為準；映射至 Vuetify theme / CSS variables，勿另引入整套 UI framework
- 若不存在 `DESIGN.md`，沿用 Vuetify 預設主題與既有頁面風格

## 全專案撰寫規則

- 降低元件、邏輯間的耦合，減少封裝、抽象化，讓程式碼盡量收束在單一檔案中。專案使用 Vuetify 統一視覺，減少自訂基礎元件。
- 新頁面請主要使用default與search-option layout並參考既有頁面進行撰寫，統一結構與畫面。
- 新表格元件請參考既有程式。
- 彈窗封裝成獨立檔案放在components/中底下，使用v-dialog + activator。

### 畫面結構與 Layout

- **殼層**：`app.vue` 為 `Sidebar` + **`v-main`**（`height: 100vh`、`overflow: hidden`），內層 **`pa-5`** 再放 **`NuxtPage`**；**禁止整頁捲動**，捲動由各頁／區塊內自行處理。
- **`layouts/default`**：單一內容卡，具名 slot **`content`**(內容區塊)。
- **`layouts/search-option`**：上 **`search`**（搜尋控制欄）+ 下 **`content`**（內容區塊）。
- search-option layout 為操作API傳入變數使用，#search template 中僅顯示操作API傳入變數選項，操作或篩選回傳資料選項應顯示在 #content template中。若無需操作API變數，則使用default layout，操作或篩選回傳資料選項應顯示在 #content template中。

## 工具函數與抽象化原則

實作前請先**搜尋**專案（`composables/`、`library/`、`config/`）。

- **除非透過封裝為composable或library後能夠大量減少重複程式碼**，**否則以不新增composable與library檔案的做法為主**，**減少抽象化與封裝達成低耦合、易讀的效果**。
- 邏輯僅在單一頁面／元件使用時，直接寫在對應的檔案中，不進行封裝。
- 確信需要抽成共用工具時，**先詢問開發者**。

---

### HTTP／後端（`apis/index.ts`）

- 新增 API 請沿用檔內既有模式（`BackendSite`、`ApiResponse<T>`；呼叫端依慣例解構 `{ data, error }`）。
- **不要**在元件中直接使用裸 `fetch`。

---

### 元件component

- 盡量減少component的封裝，除非需要被重複引用或是元件過於肥大(封裝後易於閱讀)，否則盡量把元件收束在同一檔案中。
- 實作前請先搜尋專案中 `components/global`內的複用元件。

---

## 狀態管理（`store/`）

- **全域變數**，也可以當作頁面專屬的狀態管理減少Prop Drilling(在單一頁面中的元件間方便傳遞或共用變數，例如 `XXXPageStore`)。

---

## CSS 樣式

- 樣式**寫在各自的頁面或元件檔案中**，禁止建立獨立的樣式檔案。
- **禁止在/styles中新增檔案**，樣式遷移到元件中。

---

## 路由與導頁

- 導頁一律使用 `NuxtLink` 或 `navigateTo`，不使用其他方式。

---

## SSR 與執行時機

本專案 Nuxt **預設關閉 SSR**。

## 溝通原則

- 需求模糊或有多種合理實作方式時，**先詢問開發者**，不要自行推定並實作。
