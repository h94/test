## 摘要

本文詳述 Z 幣報表後台系統的實作方案，涵蓋 API 設計、前端組件規劃與資料聚合方式。系統需提供玩家預測、賽事預測、其他 Z 幣來源及股票交易等維度的查詢報表，並透過 predictservice、tradegameservice 等取得原始資料，再由後端（beckendservice/PredictController）整合會員資訊與賽事資料。前端基於 Vue/Nuxt 3 實作多個 Tab，支援排序、展開細節與總計計算。開發過程大量使用 Cursor AI 生成程式碼，僅保留人工測試與 code review。本文對 AI 開發的幫助在於理解報表系統跨服務串接、資料過濾與畫面交互的具體規範。

---

## 關鍵業務規則

- - 一般玩家 Z 幣預測：predictbets_{gtype} 表中 strategy_id=0 且 usezcoins=true 才納入統計。
- 排除機器人：多個報表 API 需調用 memberProvider.GetRobots(999) 取得機器人帳號，並過濾掉來自機器人的交易或記錄。
- Z 幣其他來源（GetZCoinReportByOthers）過濾規則：GameUserWallet.Type = 1 且 typeInfo 中不包含「betpool 」則跳過不處理（只處理 type=1 且包含 betpool 的交易）。
- 股票交易報表收入計算：trade_type = 'buy' 時，單筆交易收入 = -(stock_price * num)；trade_type = 'sell' 時，收入 = +(stock_price * num)。
- 報表查詢參數：start_date/end_date 若未提供則預設為今天；lid/gid 為選填，聯盟選「全部」時不傳 lid。
- 前端報表總計：第一層 Grid 下方顯示總筆數（sum(betCount)）與總收入（sum(betSum)），即使結果為 0 也要顯示。

## 關鍵設計決策

- - 採用 Cursor AI 輔助開發，僅保留人工測試與 code review，降低手寫程式比重。
- 前端畫面先透過 Pencile 產生原型，再由 Cursor 生成完整程式碼，提升開發效率。
- 取得比賽資料時使用 PriceCenterProvider.GetDateGames 批次查詢，避免逐個調用 API 以提升效能，且 GDate 欄位不可能為 null，無需額外處理。
- 報表資料聚合：以 beckendservice 的 PredictController 為中樞，調用 predictservice、memberservice、pricecenterservice 獲得原始資料，再組裝成報表所需的巢狀結構。
- 前端每個 Tab 的查詢結果皆支援排序，並在展開的巢狀 Grid 中也保留排序功能，排序以 API 輸出結果為準，前端不重新請求。
