## 摘要

本文定義 TPCrawlerService 的完整技術設計：以 aiokafka 非同步消費賽事訊息，經 asyncio Queue 與固定間隔 Gate 進行批次 staging，透過 asyncpg 將資料寫入 PostgreSQL（依球種後綴的表結構）。內容涵蓋 Kafka payload 結構、PostgreSQL 欄位對應規則、寫入順序（聯盟→隊伍→賽事→賠率）、offset 管理策略、錯誤處理及動態表名 pattern，並收斂多項實作細節，為開發該爬蟲服務提供精確的資料流邊界與實作指引。

---

## 關鍵業務規則

- - Kafka offset 只在本次 flush 的所有 staging 寫入成功後才 commit，失敗則回灌 batch，不 commit offset，確保不遺漏且不重複落庫
- 若 commit offset 失敗，不回灌 batch，避免重複寫入資料庫
- 賠率表 siteodds_{suffix} 每一筆 payload 的 Odds 陣列中，一個 PlayMode 對應資料庫一筆 row，以 (game_id, market_type) 為唯一鍵，odds 欄位採 JSONB 格式 {"Prices": [<原陣列>]} 整包寫入，不做解析或正規化
- 賽事狀態 (status) 直接寫入 payload 原始字串，不做語意轉換；若為 None 或空字串，fallback 為 'Scheduled'
- gamedate 與 gametime 為必填，parse 失敗則整筆賽事捨棄，不寫入資料庫
- Score1/Score2 值若為 -1 表示賽前未開賽，寫入 NULL 到 match_h/match_a
- 聯盟、隊伍的 names（多語對照）crawler 不寫，保持 DDL 預設 '{}'；lid/tid 亦不寫，留給 Mapping 階段處理
- 賽事 UPSERT 時不覆蓋 is_fixed、gmode、gid、result 等非 crawler 管轄欄位，保留其他系統或人工已寫入的值
- source 欄位長度限制為 VARCHAR(20)，crawler 直接寫入原 site_key，若長度超過則丟棄並警告
- 球種一致性檢查：payload.GameType 需與 CLI 傳入的 sport_suffix 相符（忽略大小寫），否則整條 envelope 丟棄
- Queue 滿時直接丟棄訊息並 log Warning，不做重試或阻塞

## 關鍵設計決策

- - 採用 asyncio Queue + Gate 批次設計，將高頻寫入轉為固定間隔（預設3秒）的批量 staging，以降低對 PostgreSQL 的鎖競爭
- 使用 TEMP 表 + COPY 將批次資料快速載入，再以 INSERT … ON CONFLICT DO UPDATE 實作 UPSERT，避免逐筆 upsert 的效能問題
- 寫入順序強制為 聯盟 → 隊伍 → 賽事 → 賠率，確保外鍵依賴；上游 id 無法解析時丟棄下游列，避免整批因 FK 錯誤 rollback
- 手動管理 Kafka offset，由服務層決定 commit 時機，將寫庫成功與消費進度綁定，達成至少一次語意並避免重複落庫
- 賠率 odds 以 payload 原始 Prices 陣列直接包進 JSONB object，不進行正規化或重組，符合 DDL 的 CHECK jsonb_typeof='object' 約束，並簡化 crawler 責任
- 啟動時執行 warmup 快取，預載 gamedate 窗口內的賽事關聯資料，減少首次查詢的 DB 負擔
- 將 siteodds_{suffix} 的 game_id 由 external_game_id 對齊修正為 sitegames_{suffix} 的內部 BIGINT id，透過 flush_games_staging 後的 JOIN 取得，確保 FK 正確
- 採用 Provider/Service/Tasks 分層架構，將 IO 操作、業務流程與背景任務職責分離，符合既有 async-service 策略

## 注意事項

- ⚠️ - ⚠️ gmode 欄位來源未定（Q15 凍結），payload 樣本中無對應欄位，crawler 暫寫 NULL，待業務拍板後擴充
- ⚠️ aidata/db/games.sql 中的 sitegames DDL 為待同步舊版（status default 'pending'），與規範 DDL（postgresql_last.txt）及 payload 實際值不一致，DBA 需同步
- ⚠️ siteodds_{suffix} 的 primary key 設計與先前錯誤假設不同，實作時務必使用內部 game_id 而非 external_game_id
- ⚠️ 多球種同時執行且 topic 重疊時，同一個 consumer group 可能導致 partition 競爭與資料錯位，需在部署時注意隔離
- ⚠️ 賠率表 siteodds 不主動刪除資料，若 payload 中 Odds 為空陣列，僅跳過寫入，遺留舊 row 需後續清理
