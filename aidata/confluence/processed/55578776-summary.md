## 摘要

本文件定義了台灣運彩爬蟲的完整技術實作：使用單一 API 端點並以 POST 傳遞 payload，通過 cloudscraper 繞過 Cloudflare；payload 中的 contentId 隨不同功能改變 type 與 id 組合。分別說明 pregame（5 步 API 取得完整數據）與 inplay（3 步獲得即時比賽）的呼叫序列，以及賽果資料每 2 分鐘輪詢、並僅發送一次到 Kafka 的規則。對 AI 開發而言，可直接依據此規格實現 crawler 服務的台灣運彩模組，確保數據抓取、狀態更新與事件發布的正確性。

---

## 關鍵業務規則

- - 賽果 API 每 2 分鐘調用一次，若有回傳資料則視為比賽結束，需將該場比賽資料發送至 Kafka，且同一場比賽只發送一次。
- 前三次 API 的 type 統一為 'boNavigationList'，第四次為 'eventGroup'，第五次為 'event'。
- Inplay 流程中，列表 API 的 type 為 'inplaySportListBySportType' 且 id 為空字串；球種 API 的 type 為 'liveDataSummaryAdvancedListBySportType'，id 格式為 '球種代號/0'。
- Payload 中的 clientContext 固定 language 為 'ZH'，ipAddress 為 '0.0.0.0'。

---

## 關鍵設計決策

- - 選擇 cloudscraper 庫來處理 Cloudflare 防禦，確保請求成功。
- 所有操作共用同一個 API 端點，透過變動 payload 的 contentId 區分不同資料請求，避免多個端點管理。
- headers 固定模擬最新 Chrome 瀏覽器，降低被阻擋風險。
- Pregame 設計為連續 5 次 API 呼叫以獲取完整賽事與賠率資料，取代單次複雜查詢。
- 賽果採用輪詢方式每 2 分鐘檢查，而非依賴推送，簡化實作並可控去重。
