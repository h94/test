## 摘要

本文定義了賽事站台根據會員關注動態調整輪播的功能規範，包含：登入後的關注行為、以 GameLive 資料篩選展示邏輯、5筆/10筆輪播門檻與補齊規則、比分變化通知、前端 cache 策略，以及 API 由 PriceCenterSite 統一入口並轉發 MemberService 的職責分配。讀完後能清楚理解此功能的完整業務流程與服務間協作方式。

---

## 關鍵業務規則

- - 關注功能必須登入會員，後續請求帶有 authkey 進行驗證
- 會員登入後請求關注賽事 API，若有任何關注的賽事存在於 GameLive 中即顯示；若完全無關注或所有關注賽事皆不在 GameLive 內，則輪播顯示預設 hot game
- 預設 hot game 輪播時，隨機抽取 5 筆進行展示
- 會員有關注賽事時，若關注賽事筆數小於 5 筆，則從 hot game 補齊至 5 筆；若大於等於 5 筆，則完全不使用 hot game（僅顯示關注賽事，且最多 10 筆）
- 輪播資料總數 ≤ 5 筆時不啟用輪播功能（靜態顯示），大於 5 筆才啟動輪播
- 輪播上提供取消關注的操作，觸發取消關注 API
- 僅當會員有關注的賽事比分發生變化時才彈跳視窗通知，預設 hot game 不會觸發通知
- 前端取得關注資料時先檢查 cache，若有新增或移除關注則同步更新 cache；首次取得關注資料後寫入 cache
- 過期關注賽事由 MemberService 的 xxl-job 每日自動清除，條件為日期在兩天前的記錄（清除前兩天之前的所有關注）
- DB 表 focus_games 以 gdate（賽事日期）+ authkey（會員 authkey）為主鍵，games 欄位為 list<text>，存儲格式為「gametype + gid」，例如 BK_isagid2022-06-07
- API 流程：PriceFrontendSite → PriceCenterSite（驗證 authkey/focusdata）→ MemberService（資料驗證、解析、DB 操作），回應 msgcode 後前端處理 cache

## 關鍵設計決策

- - 將關注賽事的新增/取得/取消的 API 入口統一交由 PriceCenterSite 負責認證與路由，實際業務邏輯由 MemberService 執行，降低前端與多個服務直接耦合
- 選擇前端快取關注資料以減少重複請求，並在資料變動時即時同步，改善使用者體驗
- 過期關注賽事由 xxl-job 排程清除而非即時清理，避免對會員操作過程造成延遲，並簡化邏輯
- 關注的賽事必須存在於 GameLive 中才對外顯示，強化了資料一致性與有效性
