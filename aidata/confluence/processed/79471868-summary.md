## 摘要

為 PriceBackendService 的 Z 幣報表新增商城兌換 Tab，定義 ProductService 新 API（一次回傳 redeem logs 與對應商品清單），BFF 再向 MemberService 取得錢包扣款來加總 Z 幣，明確規則：只計算成功交易、排除退款與機器人、Z 幣以錢包 Amount 為準。文件包含 API 路徑、回傳結構、前端改動點及多項實作注意事項。

---

## 關鍵業務規則

- - Z 幣統計僅包含 product.product_store_redeem_logs 中 status = '1'（Success）的記錄，審核中（2）等狀態不計入。
- Z 幣金額來源為 gameusers_wallet_transactions 表中 Type = 3 的交易，且必須排除 PType = 'refund' 的退款交易。
- 所有 PClass（含 inplayz）皆列入計算，不排除任何類別。
- 排除 Robot 玩家，透過 MemberService.GetRobots 取得 HashAuthString 名單並過濾。
- 對帳以錢包交易 Amount 為準，不得使用 products_store.Price 推算；若成功兌換記錄找不到對應扣款，應記錄 log 並略過。
- 前端新 Tab 顯示「總筆數」與「總消耗 Z 幣」，而非「總收入」。
- 兌換記錄與錢包交易的對應鍵為 TransactionRedeemInfo 中的 Account、PClass、PID、AddTime、ID。

---

## 關鍵設計決策

- - 第一版採用全量讀取 product_store_redeem_logs + 記憶體過濾（AddTime 與 status），效能不足再優化（Q2）。
- ProductService 新 API 在同一請求中回傳 RedeemLogs 與 Products 兩個 list，Products 為完整 ProductStore 並去重，BFF 不再單獨調用 GetStoreProducts（Q7）。
- Z 幣加總以錢包交易為準，不以商品價格推算，避免價格變動帶來的誤差（Q3）。
- 排除退款交易（PType=refund）與 Robot 玩家，確保報表只反映真實消費。
- BFF API 使用 GET /api/v1/member/zcoinreports/store/byproduct 與 byplayer，放置於 MemberController，Swagger XML 於實作時補齊（Q6）。
- ProductService 新 API 路徑建議為 /api/v1/store/productredeemlogs/report，與現有 API 分開，避免破壞既有呼叫端。

---

## 注意事項

- ⚠️ - ⚠️ Cassandra 查詢效能：採用全量讀取 + 記憶體過濾，上線後需加 log 監控耗時，若變慢再優化（分區迭代、索引等）。
- ⚠️ 審核中已扣款但未成功：status=2 的記錄即使曾扣 Z 幣也不會出現在報表，營運若需調整定義需另開需求。
- ⚠️ Z 幣對帳失敗：若成功兌換找不到對應 Type=3 扣款，應記錄警告 log 並略過，不可任意填 0 或商品價格。
- ⚠️ 對應鍵不一致：TransactionRedeemInfo 與兌換記錄的欄位（Account, PClass, PID, AddTime, ID）必須一致，否則對帳失敗。
- ⚠️ 商品 join 缺漏：若 products_store 中 pid 已不存在，ProductService 需回傳 Product=null 或空 PName，避免 BFF NRE；Z 幣仍以錢包對帳為準。
- ⚠️ product-detail.md 提到 account、地址等欄位不宜對外暴露，內部後台仍應只回傳營運必要欄位。
