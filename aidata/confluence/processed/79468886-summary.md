## 摘要

本文件定義了新運彩（NewLottery）論壇系統的完整 API 服務設計，涵蓋看板、討論串、留言及按讚四個核心模組。文件詳細說明了 Cassandra 與 Meilisearch 的資料庫結構，以及 15 個 REST API 端點的路由、請求參數與回應格式。對 AI 開發 communityservice 最有幫助的是：1) 明確的 DB schema 與索引策略（Cassandra用於看板儲存，Meilisearch用於高效全文檢索與排序）；2) 完整的字數限制與重複檢查等業務驗證規則；3) 按讚功能透過獨立的 newlottery_likes 索引實作，並需防止重複按讚。

---

## 關鍵業務規則

- - 看板: 名稱最少 1 個字，且不能與先前已存在的看板名稱重複（names 欄位為 map<text,text>，需確認重複檢查是比對整個 map 還是特定語言值）
- 看板: 狀態 status 只接受 1（顯示）或 0（隱藏）
- 討論: 建立討論時，標題 (subject) 字數限制為 1-100 字，留言內容 (comment) 字數限制為 1-2000 字
- 討論: 編輯討論內容時，標題驗證規則與建立時相同（1-100 字）
- 留言: 建立/編輯留言時，留言內容 (comment) 字數限制為 2000 字（未明確說明最小字數限制，需人工確認）
- 留言: 若回覆 (respond) 其他留言，被回覆的留言 ID 必須存在，否則回傳 400 錯誤
- 按讚: 同一使用者對同一討論或留言只能按讚一次，重複按讚會回傳 409 Conflict 錯誤
- 按讚: content_type 欄位區分按讚對象為 'subject'（討論）或 'comment'（留言），當按讚類型為 subject 時，comment_id 欄位應為空白
- 圖片: 留言或討論中包含的圖片，其上傳路徑中的日期應使用「討論的發文日期」，而非留言的建立日期

## 關鍵設計決策

- - 使用Cassandra作為看板 (newlottery_forums) 的儲存：推測是因為看板數量有限、欄位簡單，適合用分散式 KV 儲存
- 使用Meilisearch作為討論 (newlottery_subjects)、留言 (newlottery_comments)、按讚 (newlottery_likes) 的儲存：目的是利用 Meilisearch 的全文檢索能力以支援未來的搜尋功能，並使用其 sortable/filterable 屬性支援排序（按留言數、按讚數、最新留言時間）與過濾（依看板 ID、狀態）
- 討論分頁 API 回傳 next_page (bool) 而非總頁數：簡化實作，客戶端僅需知道有無下一頁即可進行無限滾動或翻頁
- 按讚功能以獨立的 Meilisearch 索引 (newlottery_likes) 實作，而非在討論/留言索引中嵌入陣列：這可以避免頻繁更新核心業務文件的複雜度，並將按讚人清單的查詢獨立出來
