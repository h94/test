## 摘要

本文件為 TradeGame 功能的完整技術設計，定義了對外 REST API 的端點、輸入輸出模型、業務規則、錯誤處理策略，以及內部服務（tradegameservice）的對應關係。它明確了開發順序（先凍結對外 I/O 契約，再實作 DomainService），強制要求參考 aidata 中的 .cursor_rules 與 tradegameservice.json。對 AI 開發者而言，這份文件提供了可直接實現的 API 契約與下單業務邏輯，包含盤口比對、餘額與持倉檢查等具體規則，並說明了如何與既有 PredictService 的錯誤及語系富化模式保持一致。

---

## 關鍵業務規則

- - 下單時 trade_price 必須為整數且落在 1 到 99（含）之間，不符合則交易失敗
- 下單價格必須等於從盤口快照 Odds 中依 Mode/Spread/OddType 三層索引讀出的最新價格，不一致則失敗
- 下單前必須透過 IMemberProvider.GetGameUserData(authKey) 取得 account，若使用者不存在（null）則回傳失敗，錯誤訊息與 PredictService 的 BadRequest("key") 一致
- 買入 (buy) 時，總成本 (trade_price × stock_num) 不可超過 GameUserWallet.Balance，否則餘額不足失敗
- 賣出 (sell) 時，必須先查詢該場賽事的持倉 (TradeHolding)，且持有的 stock_num 必須大於或等於下單的 stock_num，否則失敗
- trade_type 只能為 'buy' 或 'sell'（不分大小寫），其他值一律失敗
- 對外 API 不接受 account 參數，由服務端根據 authKey 自行查詢後填入下單請求
- 取得使用者單日交易倉時，需根據每筆持倉的 mode_spread_type 拆分為三段，並從對應賽事快照的 Odds 中讀取 NowPrice，讀取失敗設為 0
- 所有回應中需要顯示賽事/聯盟/隊伍名稱時，必須在服務端依 lang 參數補齊對應語系，不要求前端二次呼叫；若富化失敗，欄位可為空但不應拖垮整支 API
- 下游 tradegameservice 回應非 200 時，須將 Error body 中的 message 及 status 轉為 ECException 拋出，格式與 PredictService 一致

## 關鍵設計決策

- - 採用三階段開發順序（Model+Provider → Controller I/O 凍結 → DomainService），避免在對外契約未確認前反覆修改 Service，此為明確的流程設計
- 所有與 PredictService 重疊的錯誤處理（如 authKey 無效、參數錯誤）完全對齊 PredictService 的 ECException 用法，確保前後端錯誤格式一致
- 語系與賽事資訊富化工作全部放在 TradeGameService 內，使用 IGameProvider、IFileProvider、IGameTransfer 等元件一次補齊，減少前端整合複雜度
- 對內呼叫 tradegameservice 的 OpenAPI 定義（tradegameservice.json）和專案 C# 開發規範（.cursor_rules）被設為強制參照來源，所有實作必須以這兩份文件為準
- TradeGameOdd 模型刻意不包含 GameOdd 的 PredictCount，以區隔預測與交易功能的回傳結構

## 注意事項

- ⚠️ - ⚠️ authKey 與 account 是否永遠一對一仍需確認，若未來 tradegameservice 改為直接接受 authKey，Provider 需調整
- ⚠️ 權限控制（下單、讀取持倉是否需要額外 token/session）文件未明確定義，留待 ECFramework 中介層決定
- ⚠️ 快取策略（如 GET tradegames 是否加 [RequestCache]）未定案，需視盤口更新頻率再評估，且要注意富化內容的即時性
