## 摘要

本文件為 AI Review Server 的完整技術開發計畫，定義如何接收 GitLab Webhook（Push / Merge Request）並自動化進行 Code 與 Plan 的 AI 審查，結果寫入 PostgreSQL，並在發現問題時通知 Rocket.Chat 及回寫 MR Comment。方案採用 DB-first + Channel<T> 佇列與 BackgroundWorker 以確保可靠性，明確將 AI 審查定位為 advisory（顧問性質），絕不阻擋 Jenkins 部署流程。對 AI 開發此服務有幫助的關鍵資訊包括：完整的分層架構（Controller/DomainService/Infrastructure）、API 端點設計、Queue/Worker 機制、錯誤處理與補償策略、以及與既有 ECCore framework 的整合方式。

---

## 關鍵業務規則

- - AI Review 結果僅為 advisory 顧問性質，不阻擋、不延遲、不控制 Jenkins 打包或部署流程，即使 AI 驗證失敗或 Provider 不可用，發版是否繼續由人工判斷
- Push Webhook 所有 branch（含 main/master）均觸發審查
- MR Webhook 僅處理 action 為 open、update、reopen 的事件，merge、close 不觸發審查（僅記 log）
- 同一 project_key + commit_sha + event_type 的重複 webhook 由 PostgreSQL unique index 防重，重複事件直接回傳 202，不重複建立 review_events
- Push 審查為輕量檢查，僅檢查 _plans/ 目錄，即使無 _plans/ 變更仍需建立 review_events 與 review_runs（可標記 skipped），並依事件型別進行結果回寫
- MR 審查為完整檢查，建立 code 與 plan 兩筆 review_runs
- 通知規則：僅 fail（critical / high）時透過 Rocket.Chat 通知，同一 (project_key + commit_sha + review_type) 24 小時內不重複通知
- AI 全部不可用時，review_run 狀態設為 ai_unavailable，並發送 Rocket.Chat 通知，不影響 Jenkins 流程
- AI 回應 JSON schema 驗證：review_type、summary、issues 必填，issue 的 severity 僅允許 low/medium/high/critical，驗證失敗則記錄錯誤並觸發重試
- Rules Repo 拉取失敗時，該次 review_run 標記 failed，不使用過時快取（避免規則不一致），CompensationWorker 下次掃描時自動重試
- 大 diff 超出 MaxDiffSize 時，分批呼叫 AI 再合併結果，合併後依 review_type + file_path + rule_id + title + line_range 去重，衝突取最高 severity

## 關鍵設計決策

- - 採用 DB-first + Channel<T> 佇列架構：Controller 收到 Webhook 後先寫入 PostgreSQL（pending），再放入 Channel；Background ReviewWorker 消費處理，確保服務重啟後可恢復
- AI Review 定位為 advisory，不控制 CI/CD，實施標準的「監督、提醒、紀錄」三方模式，避免干擾已有穩定的 Jenkins 部署流程
- 使用 System.Threading.Channels 的 BoundedChannel 作為內部佇列（預設容量 100），搭配 SemaphoreSlim 控制並行 AI 呼叫數量，提供背壓機制
- Rules Repo 採用獨立 git clone（透過 HTTPS + Token），每次 Review 前執行 git pull 檢查更新，LocalPath 存放在 Docker Volume 中常駐
- Infrastructure 層的 GitLabProvider 與 AIChatProvider 使用原生 HttpClient 呼叫第三方 API，而非 ECCore 的 IRestfulClient（因後者設計用於內部 Gateway）
- ReviewRepository 使用 ECCore 的 IPostgreSQLManager + IDbPostgreSQLCommand 操作資料庫，保持與框架一致
- 補償機制由 ReviewCompensationWorker 實作：啟動時立即掃描 pending/processing/failed 事件重新入隊，之後每 5 分鐘定時掃描，並定期 git pull rules repo
- MR Comment 採用 Append 策略（每次新增一則評論），不實作 upsert，以快速上線並控制複雜度
- Webhook idempotency 依賴 PostgreSQL unique index（project_key, COALESCE(commit_sha, ''), event_type），寫入遇 duplicate key 時直接回傳 202
- 大 diff 分段處理策略：以 MaxDiffSize 切割，逐段呼叫 AI，最終合併 issues 並去重，容許單段失敗但要記錄並繼續

## 注意事項

- ⚠️ - ⚠️ 所有 API Key / Token / 密碼以明文直接寫入各環境 appsettings.{env}.json，無使用環境變數或 secret manager，內部使用情境下接受此風險，但若外部擴展需注意資安
- ⚠️ MR Comment 回寫採 Append，存在洗版風險（小團隊流程與人為約束控制中），但未實作 upsert 或 comment 去重
- ⚠️ CompensationWorker 不實作分散式鎖定，允許極端情況下重複入隊或重複處理，需留意日誌追蹤即時性
- ⚠️ Dockerfile 需額外安裝 git CLI，部署時務必確認基礎映像相容性
- ⚠️ 目前所有 Q&A 項目均已確認，但文件版本 v1.1，若後續有變更需重新對照最新開發決議
