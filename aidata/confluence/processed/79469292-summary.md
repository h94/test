## 摘要

本文件記錄使用 Cursor AI 搭配 .cursor_rules 開發同步服務的實務經驗。核心流程為：從 Kafka 訂閱 GameData，以正規表達式篩選指定 GameType 的訊息，比對記憶體中的 Game mapping（格式為 Site_GameID），命中後解析 Odds 並更新對應的 {gameType}_param 表。其中使用 Queue 與 Thread 進行批次處理，並每 5 分鐘從 MySQL 載入近三天內 result_h 不為 -1 的比賽 mapping 至記憶體，供跨執行緒查詢。

---

## 關鍵業務規則

- - 從 Kafka 接收的訊息，必須先以正規表達式檢查是否包含 AppSetting 中定義的 GameTypes 值，不符合則丟棄。
- Game mapping 快取的內容為比賽的 gameid 與 mapping 資料（格式：Site + "_" + GameID），僅載入昨天、今天、明天中 result_h 不等於 -1 的比賽。
- 快取每 5 分鐘更新一次，且必須能夠跨 Thread 安全存取。
- 當 Queue 中的資料與記憶體 mapping 比對時，若無命中則直接拋棄該筆資料。
- 命中 mapping 時，解析該 Game 的 Odds 欄位，並更新資料庫中對應的 {gameType}_param 表（schema 參考 bk_param）。

---

## 關鍵設計決策

- - 使用 Queue 暫存 Kafka 訊息，並以 0.01 秒間隔取出，發起 Thread 進行批次處理，以控制處理頻率。
- 採用記憶體快取儲存 Game mapping，減少對資料庫的即時查詢壓力，並以定時任務（5 分鐘）維持快取新鮮度。
- 透過 .cursor_rules 與範本專案規範 AI 產出的程式碼結構、套件使用（logger、MySQL 等皆使用公司套件）、分層設計，提升生成品質與一致性。
