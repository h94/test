## 摘要

本文件定義了 TCZB 團隊執行 Sprint 的標準流程與各階段檢查清單，從估時、需求分析、開發、測試到上線與回顧，共 14 個步驟。內容涵蓋每日管理事項、Story 規模與 Design Review 觸發條件、API 變更時的 Gateway 與 Swagger 檢查，以及 JIRA 工作記錄與 Bug 收斂的監控要求。對於 AI 開發而言，這份文件可作為自動化 Sprint 管理、提醒與合規檢查的規則基礎。

---

## 關鍵業務規則

- - 專案 Sprint 開始前，SM 需與需求方確認 Story、安排開發測試分析、請需求方講解需求，並與團隊討論時程後公告
- 建立 JIRA Sprint 時，必須同時建立 Confluence 需求分析頁面、建立 Git 分支、執行 Sonarqube 取得警告數和 UT 覆蓋率
- Story 估計點數為 13 時，必須召開 Design Review
- Kickoff Meeting 須進行 StoryPoint 估算、安排 Release/Launch 負責人及 Code Review 人員
- Code Review 後必須確認所有審查內容都已修改或被記錄
- 如有新增 Service 或 API 接口，需檢查 Gateway 是否已配置，並修改對應的 swagger.json
- 每日需確認成員填寫 JIRA Work Log，測試階段要監控 Bug 數量是否收斂
- 測試後期請成員補齊分析文件，下班前需確認 JIRA 問題與回覆均已填寫
- 線上問題需長期關注時，應在 JIRA 上建立 Task 持續監督
- Sprint 結束時需結束 JIRA Sprint 並回報 PRD 監控結果
