## 摘要

本文件為 TPHubService 與 TPCrawlerService 的初始技術設計。TPHubService 負責以非同步方式將 WebSocket 訊息送至 Kafka；TPCrawlerService 從 Kafka 消費訊息，經由內部 queue 與快取網關檢查關聯後，使用暫存表批次寫入 PostgreSQL 的 sitegame、siteleagues 等分表。文件包含 Kafka 測試環境、主題對映、球種代碼、模組分層，以及避免逐筆查詢的效能優化策略，並留有部分待討論項目。

---

## 關鍵業務規則

- - 每個站點（1xbet, playbet, panda）有獨立的 WebSocket 端點與對應的 Kafka topic，例如 1xbet 對應 topic tp_1xbet。
- 資料入庫順序必須為：聯盟(siteleagues) → 隊伍(siteteams) → 賽事(sitegame) → 賠率(siteodds)，前一步失敗則不寫入賠率。
- 以 3 秒為週期從 queue 取出資料進行批次處理。
- 快取以 (source, external_id) 為鍵記錄已確認存在的聯賽、隊伍、賽事，若未命中則需插入對應表，插入衝突時採用 UPDATE 處理（即 UPSERT 語意）。
- 不同球種的資料儲存於 sitegame_xx、siteleagues_xx、siteteams_xx 等分表，xx 為球種代碼小寫（如 bk 為籃球）。

---

## 關鍵設計決策

- - 採用全非同步技術棧：websockets, aiokafka, asyncpg，以提升吞吐量。
- TPHubService 將 WebSocket 訊息改為非同步寫入 Kafka，取代原有同步方式。
- TPCrawlerService 使用 Kafka consumer 非同步拉取後先放入內部 queue 解耦，再以 3 秒間隔批次處理，減少資料庫瞬時壓力。
- PostgreSQL 寫入採用暫存表 + 批次 UPDATE + 批次 INSERT 策略，而非逐筆 upsert，並利用 asyncpg 的 COPY 或 execute_values 加速。
- 服務分層：provider 負責 I/O，service 負責業務邏輯與呼叫 provider，appsettings.py 管理連線與站點資源，taskS 處理心跳，main 負責初始化連線。
