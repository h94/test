## 摘要

這是一份 Sprint 運作流程文件，定義了從需求估算、開發、測試到上線的標準化步驟與各角色的檢查清單。對 AI 開發的幫助在於：(1) 了解團隊的開發節奏與關鍵里程碑（如 Kickoff、Code Review、Demo、Launch 時間點）；(2) 提供具體的流程檢查項目，例如 Story Point 大於 13 需召開 Design Review、Release 時需檢查 Gateway 配置等，可作為自動化流程機器人的規則基礎；(3) 明確了 Daily Checklist 與各階段產出（如 JIRA Work Log、分析文件），有助於設計進度追蹤或提醒功能。

## 關鍵業務規則

- - Sprint 時程規劃階段（Day-3）：SM 需與需求方確認 Story、安排開發與測試分析、請需求方講解需求，並討論時程後公告。
- Sprint 建立階段（Day-2）：需建立 JIRA Sprint/Story/SubTask、Confluence 需求分析 Page、Git 分支，並執行 Sonarqube 取得警告數與 UT 覆蓋率。
- 需求分析階段（Day-3 至 Day 0）：當 Story Point 為 13 時，必須召開 Design Review。
- Kickoff Meeting（Day 0）：需進行 Story Point 估算、安排 Release/Launch 負責人及 Code Review 人員。
- Release 階段（Day 9）：如有新增 Service 或 API 接口，必須檢查 Gateway 配置，並修改對應的 swagger.json。
- Launch 階段（Day 10）：需安排人員 Merge 主線、監控上線系統狀況，並請成員填寫回顧會議內容。
- Sprint 結束（Day 12）：需結束 JIRA Sprint 並回報 PRD 監控結果。
