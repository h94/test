## 摘要


本文件定義 BusinessMember 資料庫上後台管理者系統的完整技術設計，包含三層權限（Level 50/80/100）的操作邊界、Session Token 搭配 Redis 的登入驗證機制、管理行為強制記錄操作 Log 的規範，以及相關 API（管理者 CRUD、Log 查詢）的請求與回應格式。對 AI 開發而言，此文件提供了權限判斷的明確規則、Session 管理方式與資料表結構，可據此實作管理者功能並確保操作紀錄的完整性。

---

## 關鍵業務規則


- - 權限層級定義：Level 50（一般操作員）僅可查詢管理者資料，不可新增、修改、停用或調整權限；Level 80（管理者）可管理 Level 50 帳號（修改、停用）及查詢登入/操作 Log，不可新增管理者或調整 Level；Level 100（最高管理者）可建立管理者、調整權限、管理所有低階帳號及查詢所有操作 Log。
- 新增管理者僅限 Level 100 執行，且新建帳號的初始權限一律為 Level 50。
- 調整管理者 Level 僅限 Level 100 執行，且 Level 100 帳號的指派由系統人員處理（即一般功能不開放直接建立 Level 100）。
- 管理邊界限制：操作者的 Level 必須大於目標管理者的 Level（例如 Level 100 可管理 80 與 50，Level 80 僅可管理 50），同級或更高級別不可被操作。
- 自我操作限制：任何管理者皆不可修改自己的 Level，也不可停用自己的帳號。
- Log 紀錄規範：所有新增、修改、停用、調整層級的動作，必須強制寫入 admin_operation_logs，並記錄修改前後資料（before_data/after_data）。
- 登入驗證採用 Session Token + Redis Session，前端僅保存 token，後端查詢 Redis 驗證登入狀態與權限。
- Session 過期由 Redis TTL 管理（文件示例為 1 小時），同時 session 內含 expired_at 欄位；查無 session 視為 token 無效或已過期。
- 帳號唯一性：account 為 PRIMARY KEY，email 為 UNIQUE，新增或修改時需檢查重複。
- 停用管理者透過將 active 設為 false 實現，不直接刪除帳號，且需檢查操作者 Level 大於目標管理者 Level。

---

## 關鍵設計決策


- - 使用 Redis 集中管理 Session 而非 JWT 無狀態令牌，以便能主動失效 Session（例如登出、停用帳號時立即終止連線），並利用 TTL 自動釋放記憶體。
- Session Token 本身為不可預測的隨機識別值，不攜帶任何管理者資料或權限，提升安全性，避免被偽造或猜測。
- 管理者主鍵採用 account（登入帳號），不提供修改帳號功能，保持識別一致性。
- 資料表採用 soft delete（deleted_at 欄位），而非物理刪除，確保歷史資料可追溯。
- 操作紀錄表（admin_operation_logs）冗餘保存 username，以避免管理者後續更名或停用後歷史紀錄無法辨識操作者。
- 所有時間欄位統一使用 ISO 8601 格式（如 2026-06-04T09:00:00+08:00），布林值使用 JSON boolean，空值使用 null 而非空字串。
- API 回應採用統一格式 { message, data }，錯誤訊息在 message 中以固定代碼回傳，並在 data 中附帶輔助資訊（如 current_level, required_level）。
- Log 查詢預設限制 page_size 最大值 100，未指定時間區間時建議預設查詢最近 7 或 30 天，避免全表掃描。
