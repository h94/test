## 摘要

這份文件是 PriceCenter 數據管線的早期技術研究筆記，記錄了從資料爬取、解析、傳輸到儲存的完整架構設計。核心內容包括 Crawler Agent 的設計規範（如從 Zookeeper 讀取設定、回傳請求發起時間而非處理時間）、Crawler Service 的寫入冪等性機制（基於 gettime 判斷新舊資料），以及 Cassandra 資料表的初步 Schema 設計。對 AI 開發的幫助在於：理解體育數據從外部網站到內部 DB/Redis 的流向、各服務的職責邊界、以及避免舊資料覆蓋新資料的關鍵時序邏輯。

---

## 關鍵業務規則

- - Crawler Agent 必須從 Zookeeper 讀取 Parse 邏輯設定（XPath 或 JsonPath）
- Crawler Agent 傳回的 JSON 結構中，gettime 欄位必須是「發動 request 之前的時間」，而非收到 response 後的處理時間，以反映來源網站的延遲
- Crawler Agent 需在本地暫存資料，僅在資料有變動時才傳送，並需定期清理快取
- Crawler Service 收到資料後，必須比對 sitegame cache 中記錄的前一次 gettime，若新資料的 gettime 早於 cache 中的時間，則不進行更新，以避免多個 agent 的亂序寫入造成舊資料覆蓋新資料
- Crawler Service 啟動時需從 DB 載入所有未結束（status != closed）的 sitegames 作為 cache
- Nginx 層僅負責接收 POST 請求並寫入 Kafka，不處理任何業務邏輯
- CacheService 與 Crawler Service 必須使用不同的 Kafka GroupId，以確保兩者都能消費到同一份資料
- CacheService 需定期刪除 10 分鐘前的 Redis changelog
- Integrate Service 需提供 API 供 JOB 定時執行，自動將不同網站但相同球隊、時間的比賽合併為同一場

---

## 關鍵設計決策

- - Crawler Agent 區分為兩種工作模式：讀取歷史資料與讀取即時資料，必要時可拆分為兩個 Agent，但需抽出共用函式（設計原因：不同資料源的讀取模式與時效性不同）
- CacheService 透過 Redis 的 price_maps_{gtype} 查找 gameid 對應關係，而非每次都查 DB（設計原因：減少 DB 查詢壓力，加速即時資料處理）
- Crawler Service 採用「直接寫入 DB，不進行其他業務判斷」的策略（設計原因：資料的合併、報價等邏輯交由後續的 Integrate Service 和 PriceCenter Service 處理，保持職責單一）
- Cassandra 資料模型採用 MAP 類型儲存多語系名稱（如 lname MAP<VARCHAR,VARCHAR>），並以複合主鍵設計支援時間序列查詢（如 games_BS 以 id + gdate 作為 PRIMARY KEY，gdate 採 ASC 排序）
