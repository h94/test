## 摘要

這份文件定義了新運彩（金葡京）會員系統的資料庫表格，包含 MySQL 中的 CoinWallet 錢包表與 CoinWallet_Transactions 交易紀錄表，以及 Cassandra 中的 newlottery_users 使用者表與 newlottery_commissions_betpool 彩池抽成表。文件中詳細列出各表格的欄位、型態、主鍵設計、索引，並定義了交易類型代碼（T_Type）及其對應的 JSON 格式 T_Detail 內容。這些資訊可協助 AI 理解會員錢包餘額、交易紀錄的結構以及不同場景下的資料格式規範。

---

## 關鍵業務規則

- - CoinWallet.Balance 為 int(10)，代表代幣餘額，負值可能表示扣款。
- CoinWallet_Transactions.T_Type 定義交易種類：1 門票、2 轉帳、3 買牌、4 賣牌、5 彩池獲利、6 抽成獲利、7 儲值、8 VIP購買（2026-4-21 新增）、77 測試/官方贈送。
- T_UID 欄位只有在 T_Type = 2（轉帳）時為必填，其餘類型可為 null。
- T_Detail 欄位依 T_Type 不同，儲存不同結構的 JSON 字串，例如 T_Type=1 包含 GameType 和 ChampionshipID，T_Type=3/4 包含 GameType、LID、GID、UID、ID、CID，T_Type=5 包含 GID、BType、PID、Rank，T_Type=7 包含 Year、DateTime、OrderID、SubID。開發時需依此格式序列化/反序列化。
- newlottery_users 表中 status 欄位為 int，0=未驗證、1=已驗證、2=停權。
- newlottery_users 的 contact_info 為 map<text,text>，存放 line、wechat、whatsapp 等社群 ID。

---

## 關鍵設計決策

- - 錢包與交易紀錄採用 MySQL 儲存，推測因為需要強交易一致性與關聯查詢。
- 使用者基本資料與抽成紀錄採用 Cassandra，因其適合大量寫入與水平擴展，且以 account 為 partition key 利於快速查詢。
- T_Detail 以 JSON 字串形式儲存可變結構的交易明細，避免頻繁修改 schema。
- CoinWallet_Transactions 使用 AUTO_INCREMENT 的 T_ID 作為主鍵並對 Account 建立 INDEX，優化以帳號查詢交易紀錄的效能。
- newlottery_commissions_betpool 以 gametype 為 partition key，gid 為 clustering key，id 對應鑽石交易紀錄 T_ID，用於關聯。

## 注意事項

- ⚠️ - ⚠️  T_Type=8（VIP購買）為 2026-04-21 新增，文件未提供對應的 T_Detail 範例，實現時需人工確認格式。
- ⚠️  T_Detail 中 T_Type=6（抽成獲利）格式標注為「暫定」，可能後續有調整，建議與開發團隊確認最終規範。
- ⚠️  CoinWallet 表中 Balance 為 int(10)，未明確說明是無符號還是可為負值，需查詢業務邏輯確認是否允許負餘額。
- ⚠️  文件提到「代幣交易紀錄 T_Detail」表格中 T_Type 2、6、77 的格式範例中，T_UID 只有當 Type 2 時必填，但範例中顯示 T_UID 可為 null 或字串，使用時應確保轉帳時必定傳入接收方帳號。
