## 摘要


本篇為 NewLotterySite 的技術設計文件，定義了如何在前台發文、留言、按讚及收回讚時，透過 MemberService 檢查使用者是否被禁言（水桶名單），並規範了 403/500 錯誤回傳格式與前端對接方式。同時新增訊息中心主題列表與主題過濾功能，說明資料來源、API 端點規格及實作步驟。對 AI 開發可快速掌握禁言檢查的業務規則、錯誤處理邊界以及與 MemberService 的整合細節。

---

## 關鍵業務規則


- - 發文（CreateSubject）、留言（CreateComment）、按讚（LikeSubject/LikeComment）及收回讚（UnlikeSubject/UnlikeComment）前，必須呼叫 MemberService 查詢帳號是否在 active 水桶名單，若為禁言狀態則回傳 HTTP 403 'user is banned'，禁止操作。
- MemberService 水桶查詢回傳 HTTP 404 時，視為未禁言，允許繼續原流程；若連線失敗或下游回應 5xx，必須回傳 HTTP 500 'system error'，不允許進行發文、留言、按讚或收回讚。
- 訊息中心主題列表 GET /notifications/topics 僅回傳 enabled=1 的主題。
- 訊息中心文章列表 GET /notifications 支援可選 query 參數 tid，傳入時僅回傳該主題的文章，不帶 tid 則回傳所有 enabled 主題的文章，維持向下相容。
- 文章回應中的 icon 欄位由其所屬主題的 icon 決定，並非文章本身的持久化欄位，同一主題下所有文章的 icon 相同。

---

## 關鍵設計決策


- - 沿用既有 ECException 格式，以 HTTP 狀態碼搭配 { "Error": "<message>" } 回傳錯誤，前端以 error.data.Error 字串比對決定顯示的提示文案，不引入數位錯誤碼或額外 body 結構。
- 403 禁言回應中不夾帶禁言結束時間或原因等細節，避免向前端暴露後台水桶設定資訊，使用者僅看到對應的 toast 提示。
- 實作分為 Provider、Controller I/O、Service 邏輯與整合測試四個階段，並在 I/O 定義完成後設置中止點，確保 review 後才進入邏輯實作。
- 抽取共用方法 ensureNotBannedAsync，在 CommunityService 中所有需禁言檢查的動作（發文、留言、按讚、收回讚）中重用，以減少重複邏輯。
- 訊息中心的 icon 由後端根據主題關聯帶出，而非在通知文章表中冗餘儲存，以減少資料不一致風險。
