## 摘要

本文件為 inplayz CommunityService 的完整 REST API 技術規格，涵蓋文章、回文、Hashtag、點讚、檢舉等功能的創建、讀取、更新、刪除端點，包含請求參數、回應格式與業務約束。對於 AI 開發，可直接依此規範實現對社群服務的調用邏輯，並掌握分頁策略、不可重複點讚限制、圖片路徑生成規則、Hashtag 覆蓋式更新等關鍵行為。此外，文件揭露點讚明細與 Hashtag 資料獨立存放於 meilisearch，有助於資料分離設計的實作。

---

## 關鍵業務規則

- - 文章內容最少1字，最多2000字；回文內容最少1字，最多200字。
- 建立回文時，若未提供 respCommentID 或給空字串，建立一般回文；若提供有效 respCommentID，則建立回覆回文。
- 同一 user 對同一文章或回文的同一 emoji 只能點讚一次，重複請求返回 HTTP 409。
- Hashtag 更新時，傳入的 data 參數會完全覆蓋該 hashtag 的所有語系資料（例如原有中英文，只傳入韓文則更新後僅存韓文）。
- Hashtag 語系代碼必須是 zh-CN, en-US, ja-JP, ko-KR, th-TH, zh-TW, vi-VN 之一，否則請求視為無效。
- 取得文章分頁時，每頁最多20篇；同一 hashtag type 內多個篩選值用底線分隔，篩選邏輯為 AND；回傳 next_page (bool) 表示有無下一頁，need_click (bool) 表示是否需要前端手動點擊「查看更多」。
- 圖片儲存路徑使用文章建立日期（非實際寫入日期），格式：/sport/img/community/{yyyy-MM-dd}/{articleID}/article/image{n}.webp 或 /comment/{commentID}/image{n}.webp。
- 檢舉狀態僅有 open 和 done，更新狀態時僅允許設為 done（表示處理完畢）；檢舉理由長度限制 1-100 字元。

## 關鍵設計決策

- - 點讚詳細資料與 Hashtag 數據獨立存放於 meilisearch 的 like 與 hashtag index，文章/回文 JSON 僅保留 like_count 摘要，目的是降低主文檔大小並提升查詢效能。
- 文章分頁加入 need_click 標誌，區分自動加載與需用戶手動點擊「查看更多」的情境，以控制後端壓力並提供可控的前端體驗。
- Hashtag 更新採用完全覆蓋機制（而非合併），簡化實作複雜度，由調用方負責維護完整語系資料。
