## 摘要

本文件記錄在 PriceCenterSite 中導入 TradeGame 交易功能的設計過程，提供四支 API（聯盟盤口快照、使用者單日交易明細、歷史交易紀錄、買賣下單）的完整 I/O 模型、業務規則與實作步驟，並總結使用 Cursor AI 輔助開發的經驗教訓。對 AI 開發的幫助在於：可直接依據此計畫產出符合規格的程式碼，並採用「Plan 文件 + 人工審核補強 + Agent 生成」的模式避免全自動生成時的不準確。

---

## 關鍵業務規則

- - TradeGameOdd.Odds 來源為 TradeGameProvider.GetTradeGameSnapshots 中對應賽事的 Odds，不處理 Redis 中的 Odds。
- TradeHolding 需將 TradeHistory 反序列化為 List<TradeHistoryLog> 並存入 Logs，同時計算 NowPrice（透過快照取得即時賠率）與 Profit（即時：Log 中 Profitpoint 加總 + 庫存*NowPrice；歷史：僅加總 Log 中 Profitpoint）。
- CreateOrder 時 trade_price 必須為 1~99 的整數，且必須等於快照中 Odds[Mode][Spread][OddType] 的值。
- 買入時，trade_price * StockNum 不可大於用戶錢包餘額；賣出時，用戶對應賽事的庫存 StockNum 必須 ≥ 請求數量。
- GetUserHistoryTrades 僅回傳 winloss 有值的 TradeHolding，並以 date -> gtype -> League 三層 Dictionary 結構輸出。
- GetRedisDateRangeGamesForTradePrices 僅回傳 status 為 0 或 2 的賽事，且 CreateOrder 的 gid 必須存在於該回傳結果中。
- 所有 API 的錯誤處理與回報訊息需對齊 PredictService 的既有格式。

---

## 關鍵設計決策

- - 放棄全自動生成程式碼，改為先產生 Plan 文件，經人工審核與細節補強後再由 Agent 生成，以確保輸出準確性。
- Provider 層不進行 authKey→account 轉換，直接由 Controller 傳入 account，簡化責任歸屬。
- TradeGameService 內部不直接調用 GameService 等其他服務，僅透過 IGameProvider、IFileProvider 等符合依賴倒置的方式取得資訊。
- 模型命名調整：TradeGameStockHoldingsRow → TradeHolding，TradeGameAddTradeBody → TradeOrder，提升可讀性。
- TradeGameSnapshotResponse 與 TradeGameHoldingRowResponse 的欄位設計參考 GameOdd 與 PredictGame 的輸出，確保輸出結構一致。

## 注意事項

- ⚠️ - ⚠️ 全自動生成階段 AI 經常無法準確定義 I/O Model，需人工審查並在 Plan 中補齊欄位細節。
- ⚠️ Step 7 的檢查邏輯（如 gid 存在性、狀態過濾）依賴實作順序，若後續調整 Provider 需同步確認。
- ⚠️ Profit 計算邏輯在即時與歷史交易中不同，需於 Service 層明確區分實作。
