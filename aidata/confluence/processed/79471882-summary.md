## 摘要

本文件為 Z 幣報表新增「商城-商品」與「商城-玩家」Tab 的詳細技術設計，涵蓋ProductService、PriceBackendService 與前端 Nuxt3 的 API 合約、業務對帳規則及 UI 規範。對 AI 開發的幫助在於：明確了 PS-1 端點（/api/v1/store/productredeemlogs/report）的回傳結構（redeemLogs + products 雙 list），BFF 層兩個報表 API 的請求/回應格式，以及關鍵對帳邏輯（status=1、排除 Robot、五鍵匹配、取錢包Abs(Amount)），可直接用於自動生成程式碼或測試案例。

---

## 關鍵業務規則

- - 交易成功定義為兌換紀錄 status = "1"（Success），其它狀態不納入報表。
- Z 幣消耗金額以錢包交易扣款為準：篩選 Type=3、PType != "refund"，取 Abs(Amount) 加總。
- 排除 Robot 帳號：呼叫 GetRobots(999)，對每個 wallet 的 AuthKey 進行 HashAuthString 比對，若匹配則不計入。
- 兌換紀錄與錢包交易對帳採用五鍵完全匹配：Account、PClass、PID、AddTime、ID。
- 一筆兌換紀錄若找不到對應的錢包交易，則不計入筆數和 Z 幣總和，並記錄 Warning 日誌。
- ProductService 查詢端點 (PS-1) 固定篩選 status="1"，不提供可變 status 參數，僅接受 startTime、endTime，且 endTime < startTime 時回傳 400。
- 前端 Tab 5/6 頁底顯示「總消耗 Z 幣」（而非其他 Tab 的「總收入」），文案與其他 Tab 不同。
- 商品種類不排除 inplayz，包含所有 PClass。

---

## 關鍵設計決策

- - 採用 BFF (PriceBackendService) 聚合 ProductService 與 MemberService，ProductService 一次回傳 redeemLogs 和 products 兩個 list，避免 BFF 重複呼叫商品 API，與既有 GetZCoinReportByOthers 模式一致。
- ProductService 的第一版實作採全量讀取+內存篩選，不先做時間或狀態過濾，後續再優化（第二版 Cassandra 效能優化）。
- 不修改既有 GET /api/v1/store/productredeemlogs 的行為，改用新路徑 /report，保持 backward compatibility。
- 選擇不排除 inplayz PClass（決策 Q5-A），保持資料完整性。
- 前端新 Tab 僅需日期篩選（dates-only），複用 OthersTradeTable 的 UI 模式，降低開發複雜度。
