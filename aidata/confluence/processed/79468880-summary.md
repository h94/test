## 摘要

本文檔定義了一個 Sprint 從前期的排程協調、需求分析、開發、測試到上線與回顧的標準流程，並提供各階段的具體檢查清單與責任分工。對於 AI 開發人員，此文件有助於了解團隊的開發節奏、各時間點需完成的任務範疇（如建立 JIRA 項目、Code Review、API Gateway 與 Swagger 文件更新等），以及每日站會應關注重點，從而順利融入團隊協作流程。

---

## 關鍵業務規則

- - Sprint Day(-3) 前 SM 需與需求方確認 Story，安排開發與測試分析，請需求方講解需求，並和成員討論時程後公告時程
- Sprint Day(-2) 需建立 JIRA Sprint/Story/SubTask，建立 Confluence 需求分析頁面，建立 Git 分支，執行 Sonarqube 取得警告數和 UT 覆蓋率
- 需求分析階段若 StoryPoint = 13 需召開 Design Review；確認需求分析完成後由成員評估時間
- Kickoff Meeting (Day 0) 由開發測試人員講解需求、進行 StoryPoint 估算、安排 Release/Launch 負責人、安排 Code Review 人員
- Coding 階段為 Day 1-5
- Day 4 進行 Code Review，必須確認 Code Review 內容都有被修改或記錄
- Day 4 舉行 TestCase Review Meeting
- Local Test (Day 6-8) 需確認 Sprint 進度是否正常
- Day 8 舉行 Demo Meeting
- Release (Day 9) 若有新增 Service/API 接口，需檢查 Gateway 是否有配置，並修改對應的 swagger.json（修改步驟參考 Confluence 頁面 5341691）
- PRE Test 階段為 Day 8-10
- Launch (Day 10) 需安排人員 Merge 主線、安排人員監控上線系統狀況，並請成員填寫回顧會議內容
- Day 11 舉行 Retrospective Meeting
- Sprint Close (Day 12) 需結束 JIRA Sprint，並回報 PRD 監控結果
- Daily Meeting 需了解 Member 問題，判斷是否影響時程，並盡快回報上級
- 每日確認 Members 確實填寫 JIRA Work Log
- 進入測試階段需注意 Bug 數是否收斂
- 測試後期請成員補齊分析文件
- 下班前確認 JIRA 問題和回覆都有填寫
- 若線上問題需長期關注，應在 JIRA 上建立 Task 監督狀況
