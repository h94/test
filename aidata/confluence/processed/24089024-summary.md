## 摘要

本文件定義 GameSettingService 的完整 REST API 規格，涵蓋系統設定、聯盟設定、範本設定、賽事設定四個層級的 CRUD 操作。對 AI 開發而言，最重要的是理解 SystemSettings 的資料結構（包含 PlayMode、Layout、SiteSetting、RadioCount、UseSuggest、Rate 等欄位），以及設定值如何透 API #18 提供給 ZBParser 等下游服務消費。API #19 的「替換聯盟設定檔」功能暗示設定值可被批次替換，這對理解設定值生命週期很重要。

---

## 關鍵業務規則

- - 玩法(PlayMode)的盤口數(RadioCount)若為 0，表示不使用此玩法
- FirstScore 玩法的 RadioCount 固定為 1，UseSuggest 固定為 false
- CorrectScore 玩法的 Rate 可為負值（如 -10），其餘玩法 Rate 為正整數（如 1900）
- SiteSetting 的 Mode 決定資料來源策略：'依順序' 輸出 SiteList（按優先序取用），'依比重' 輸出 SiteRate（按權重分配）
- API #3 依聯盟取得設定值時，leagues 參數為必填，格式為 JSON array of lid
- API #18 的 company 參數對應 MySQL GM 資料庫 Teams 表的 TeamName 欄位
- API #20 訂閱者註冊由 PriceBackendService 呼叫（非前端直接呼叫）
- 聯盟設定值才包含 Leagues 欄位，賽事設定值才包含 Game 欄位，系統設定值兩者皆無

## 關鍵設計決策

- - 設定值分為 System / League / Template / Game 四個層級，形成繼承覆寫的階層結構（需人工確認具體的優先序規則）
- SystemSettings 的 Settings 欄位以 List<PlayModeSettings> 設計，每個 PlayMode 可獨立設定 Layout、SiteSetting、RadioCount 等，避免一個設定值只能套用一種玩法
- API #3 的 leagues 參數設計為 Request Body 而非 Query String，推測是為支援大量聯盟 ID 的批次查詢
- 登入驗證透過 uid 參數進行，uid 由登入成功後產生，後端可透過 uid 反向取得使用公司代碼和帳號
- API #19 PATCH 替換聯盟設定檔時，透過 newSettingId 參數指向新設定值，而非直接修改原有設定，保留設定值歷史與可回溯性
- API #22/#25 的訂閱者管理帳號功能與 PriceBackendService 共用使用者管理機制，備註明確指向該服務
