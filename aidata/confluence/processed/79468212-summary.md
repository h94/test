## 摘要

本文件定義了 BoomeRang 賠率站台的爬蟲技術設計，包括 5 支核心 API 端點、17 種球種與網站 ID 的對應關係、4 種語言的 lang_code，以及從 API 回應 JSON 中萃取比賽資料（game_id、球種、聯盟、隊伍、時間、分數）的欄位路徑對照表。對 AI 開發而言，這份文件提供了完整的資料來源規格與欄位映射規則，可用於實作 crawlerservice 的資料擷取邏輯，並確保產出的賠率資料格式符合 pricecenterservice 的輸入要求。文件也說明了賽果的三種狀態（正常有分數、終止比賽 isDropped=true、無結果無標記）的判斷方式。

---

## 關鍵業務規則

- - 取得賽前比賽資料的 API（GetCouponEvents）的 startDate 參數需帶入前一天的日期才能取得今日的賽事（例如：2026-01-21 要帶入 2026-01-20）
- 球種名稱需從 API 回傳的 sport.name 進行轉換（例如：Football → SC, Basketball → BK），共定義 17 種球種對應
- 賽果資料只能分聯盟去請求，需先透過 GetSportMenu API 取得所有球種的聯盟清單，再逐個請求 GetEventResults
- 賽果中 isDropped=true 表示比賽終止（可能是延賽或取消，但無法區分是延賽還是取消）
- 賽果若完全沒有 score 欄位也沒有 isDropped 標記，屬於異常情況（未提供結果）
- 若要取得多語言賽事資料，只需在原 API 加上 lang_code 參數（支援 ja-JP, ko-KR, es-ES, fr-FR）
- 比賽時間 startDate 需再轉換時區（timezoneOffset=-480，即 UTC+8）
- scores 欄位需由 [score_home, score_away] 組成

## 關鍵設計決策

- - 選擇直接呼叫 altenar 平台的 API 而非爬取網頁 HTML，可獲得結構化 JSON 資料，降低解析複雜度
- 賽前和賽中資料使用不同 API 端點（GetCouponEvents vs GetLiveEvents），因為兩者在平台的資料結構和更新頻率不同
- 賽果查詢需要先取得完整聯盟清單再逐個請求，而非單一 API 批次取得，這是因為平台限制只能分聯盟查詢
- date 參數需帶入前一天日期的設計（帶入 2026-01-20 取得 2026-01-21 的賽事），可能是因為平台時區轉換的特定邏輯，需確保爬蟲的日期計算正確
- 聯盟名稱由 category.name（國家）和 champ.name（聯盟）組合而成（例如 Brazil-Maranhense），這是為了在資料庫中建立結構化的聯盟階層

## 注意事項

- ⚠️ - ⚠️ 賽果的 isDropped 無法區分延賽和取消，若系統需要區分這兩種狀態，需人工確認來源端是否有其他判斷方式
- ⚠️ date 參數需帶入前一天日期的規則，文件以 2026-01-21 為例說明，需確認這是否為文件撰寫當日的特定情況，還是永久規則
- ⚠️ 文件提到「一種是完全沒給結果也沒有寫終止」，這種情況下爬蟲應如何標記比賽狀態（例如標記為異常/未完成），文件中未明確定義，需與業務方確認
