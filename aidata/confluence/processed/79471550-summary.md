## 摘要

本文档规划了为 AI Review Server 新增两个后台服务（ReadmeCatalogSync 和 AidataSwaggerSync），通过独立的 Portainer 实例发现运行中的服务，依据 PostgreSQL mapping 表自动从 GitLab 克隆仓库、生成 README 并获取 OpenAPI 快照，将结果提交到 aidata 规则库。关键设计包括以 Portainer 为权威来源、用 DB 表替代 CSV、双 worker 分路径写入以避免冲突，以及基于 GitLab 提交时间与时间戳的增量检测。文档明确了各 worker 的职责、时间戳更新规则及异常处理策略。

---

## 關鍵業務規則

- - 每个 mapping 表行有两个 UTC 时间戳：ReadmeCatalogSyncLastCheckUtc（第 6 栏）记录 README 同步成功时刻，AidataSwaggerSyncLastCheckUtc（第 7 栏）记录 Swagger 检查成功时刻，两者独立更新
- 当 GitLab 默认分支无新 commit 时，不执行 AI 生成 README 且不 commit/push aidata，但仍视为同步成功并更新第 6 栏为 HEAD commit 时间
- Swagger 同步时，HTTP 成功且 JSON 内容与 aidata 现有文件相同，仍更新第 7 栏（视为成功），但 HTTP 失败（timeout/5xx/解析失败）时不更新该栏
- 无法自动对照到 GitLab 仓库时，mapping 表的 GitLabUrl 设为 NULL，且不对该行执行 clone 或变更检测
- 两个 worker 写入 aidata 的路径严格分开：ReadmeCatalogSync 仅写 */*.md，AidataSwaggerSync 仅写 webapi/**/*.json，且必须分两次独立的 commit 和 push
- 每个逻辑服务键（按 Image + PublicPort 去重）独立进行 git add/commit/push，单键失败不影响其他键，且只有在 push 成功且 DB 更新成功后才更新对应时间戳

---

## 關鍵設計決策

- - 采用独立 Portainer 实例而非 GitLab 作为服务运行状态的唯一权威来源，避免与 AI Review 部署环境耦合
- 使用 PostgreSQL 的 catalog.portainer_gitlab_mapping 表代替 CSV 文件存储 Portainer-GitLab 映射，便于人工 pgAdmin 维护，且两 worker 直接更新不同列
- 将 README 生成和 Swagger 快照拆分为两个独立的 BackgroundService，通过相位偏移错开执行，避免争锁且职责清晰
- aidata 的 pull/commit/push 复用现有 RuleProvider 的内部锁机制，不暴露锁给外部，保证与规则加载的互斥
- 首次自动对照时优先使用 Swarm 服务的 com.docker.stack.namespace 标签与 GitLab group 名匹配，失败后依次采用镜像 regex、label/env 启发式等降级方案
- Swagger 快照 worker 不从 Portainer 重新获取服务列表，仅读取 mapping 表中 ReadmeCatalogSync 维护的 OpenApiUrl 进行 HTTP 取样，降低耦合
