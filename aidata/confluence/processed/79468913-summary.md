## 摘要

本文件定義 TradeGameService 的設計目標、API 規格、資料庫結構與結單流程，用於將 sitegameoddservice 的交易功能遷移至此專案。API 提供即時股價查詢、買賣操作、用戶持股與交易紀錄查詢及賽事重新結算。資料表 stock_holdings_{game_type} 以 partition key (gdate) 和多個 clustering keys 記錄每筆交易，並透過 trade_history JSON 記錄詳細買賣歷史。結單流程透過永久迴圈掃描已結束比賽，計算玩法結果後更新 winloss 並觸發 Z 幣交易。

---

## 關鍵業務規則

- - 手續費率為賣出股價的 0.3%，公式：賣出獲利 = 賣出股價 × 股數 × (1 - 0.003)。
- 若球頭非整數（如 1.5），需拆成 spread（整數部分，如 2）與 ratio（倍數，如 100）進行計算，但在 mode_spread_type 中仍以原始 spread 字串表示。
- trade_history 記錄 JSON 陣列字串，每個物件包含 trade_type (buy/sell/refund/recalculate/resell)、trade_operator (user/system)、stock_price、num、profitpoint、trade_time。
- 使用者買賣操作時 trade_operator 為 'user'；系統結單賣出時為 'system'；取消或平手退款時 trade_type 為 'refund'；重算收回獲利為 'recalculate'。
- 結單流程：從 games 表選取 status=1 (已結束) 的比賽，找出該賽事所有 stock_holdings 中尚未賣出的股票，以系統身份全部賣出，並生成 Z 幣交易紀錄。
- 取得即時股價 GET API 可只填 gdate，但不可只填 gid。
- 買賣 API 在股票數量不足時回傳 status_code 400，訊息 '股票數量不足'。
- 重新計算賽事交易 API (PUT) 將退回該賽事所有已計算的獲利（reset），並重新結單一次。
- stock_holdings_{game_type} 表的 partition key 為 gdate，clustering keys 依序為 lid, gid, account, mode_spread_type。
- winloss 欄位值：W (玩法勝)、L (玩法敗)、C (取消)、N (平手)。

---

## 關鍵設計決策

- - 採用分表設計 (stock_holdings_{game_type}) 以提升查詢效能並隔離不同球種的交易資料。
- 選擇 gdate 作為 partition key，有利於按日期範圍查詢用戶的交易記錄。
- 使用 spread (整數) 與 ratio (倍率) 兩欄位處理非整數球頭，簡化計算邏輯的同時保留精確度。
- trade_history 以 JSON 字串存入，雖犧牲查詢索引但可彈性記錄複雜的交易序列。
- 使用永久迴圈執行緒定期輪詢 games 表來觸發結單，而非事件驅動，可能是因為無法直接監聽比賽狀態變更。
- recalculate API 的設計是退回原獲利後重新結算，確保比分修正後的正確性。
