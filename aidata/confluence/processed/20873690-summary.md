## 摘要

文件記錄了 PriceCenter 服務群備援環境（newPC）的建置任務與設計決策，涵蓋基礎設施（Docker、Kafka、Redis、Cassandra、Nginx）及主要服務的部署策略。重點在於各服務的資料讀寫邊界：多數服務僅讀取正式環境資料庫且禁止寫入，Kafka 與 Redis 獨立於備援機上運行，並透過 xxl-job 同步頁面資訊。對 AI 開發而言，這份文件揭示了備援模式下服務的弱依賴設計與異常保護需求。

---

## 關鍵業務規則

- - Crawler service 與 flow service 只能讀取正式環境資料庫，禁止寫入，且實作時必須加入 try-catch 防止讀取失敗導致服務崩潰。
- Pricecentersubscribtion service 讀取正式環境資料庫時同樣需 try-catch，不能因正式環境異常而中斷。
- Pricecenter service 讀取正式環境資料庫，但 Redis 寫入自己的備援實例，不可寫入正式 Redis。
- Python parser 需額外發送訊息到備援機的 Kafka。

---

## 關鍵設計決策

- - 備援機的 Kafka 採用 Single Node 部署，Topic 包含 gamedata 與 processgamedata，用於備援情境中的訊息傳遞。
- 備援機 Redis 獨立部署 Single Node，僅供 pricecenter 與 gateway 使用，不與正式環境共用。
- Cassandra 同樣為 Single Node，僅新增 pricecenter 資料庫與必要表（page tables, ku account），減少不必要的複製。
- Nginx 設定透過複製正式環境配置並修改路由，DNS 切換需手動進行（非自動容錯），意味發生災難時仍有人工介入步驟。
- Gateway agent 需修改程式碼，加入新備援機的 API 路由與認證資訊。
- Pricecentermanager 在備援機上獨立運行 BACKUP 模式，擁有自己的資料庫，並透過 xxl-job 定期呼叫 PRD 的 syncpage API 同步頁面資訊。
- Pricecentersubscribtion 在備援機上的設定：gtime 讀取需重構，API 呼叫本地的 gateway 與 pricecenter 並維護獨立 cache。
- Pricecenter service 的 xxl-job 需呼叫備援機的 Redis API 來寫入快取，而非直接操作正式環境。
- Crawler service 的 Kafka 讀取和寫入皆指向備援機的 Kafka 實例。
- Flow service 同樣使用備援機的 Kafka 進行讀取，資料庫僅讀不寫。
