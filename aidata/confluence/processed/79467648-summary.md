## 摘要

本文件定義了新運彩投注系統的核心功能與資料結構。主要說明了注單建立、賣牌資格管理與注單查詢的 API 設計，並規範賣牌資格的生成條件（當日賽事結束後）及 Redis 儲存規則（Key 格式為 sellrights_{錦標賽id}_{賣牌日期}，保存 3 天）。開發 PredictService 時可依此文件的 API 規格與 DB Schema 設計資料存取邏輯，並理解新運彩系統如何透過 PredictResultService 更新注單結果以複用現有球王機制。

---

## 關鍵業務規則

- - 賣牌資格生成條件：當日賽事（包含跨日比賽）全部結束後才生成。
- 賣牌資格 Redis 儲存規則：Key 格式為 sellrights_{錦標賽id}_{賣牌日期}，資格資料保存 3 天。
- 注單結果更新機制：比照球王建置，由 PredictResultService 負責。

---

## 關鍵設計決策

- - 資料分區設計：predictbets_{gameType}_newlottery 以 lid (聯盟id) 作為 partition_key，gdate、gid、uid、id 作為 clustering key，此設計適合依聯盟和日期範圍查詢注單的場景。
- API 路徑結構：依功能區分為錦標賽相關（/newlottery/championships/）與通用注單查詢（/newlottery/bets/），賣牌資格獨立為 sellrights 子資源。
- 欄位保留策略：canlock、mainbet、match_a、match_h 等欄位標注為「保留，暫不使用」，推測為後續版本功能預留空間。
- 資料儲存：賣牌資格選擇使用 Redis（非 DB）儲存，符合其時效性需求（僅保存 3 天）與快速查詢的需求。

## 注意事項

- ⚠️ - ⚠️ 文件最後更新於 2026-01-05，請確認 API 規格與 DB Schema 是否已有後續 sprint 變更。
- ⚠️ POST /newlottery/championships/{gameType}/{id}/bets 的 Request Body 與 GET /newlottery/bets 的 Response Body 欄位有所不同（如 POST 有 Odd、Point、Ratio 等，GET 多了 profitPoint、winLoss），需確認這是注單生命週期中不同狀態的資料（新建 vs. 已結算），還是 API 設計不一致。
- ⚠️ DB Schema 中 match_a 備註為「主隊比分」、match_h 備註為「客隊比分」，但許多運動項目中 match_h 通常代表主隊，此處備註可能相反，需人工確認。
