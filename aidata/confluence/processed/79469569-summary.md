## 摘要

這份文件定義了兩個功能模組的實作方案：一是熱門彩池賽事 API，利用 PriceCenterServer 既有的設定/取得熱門場中競猜賽事 API，透過 PriceBackendService 轉發請求，其中設定 API 若發現賽事已存在會先清空舊資料再寫入；二是 Z 幣排行過濾機制，直接在現有「取得錢包資訊」API 的 Domain Layer 中加入過濾邏輯，使用既有的 skipRobotUser() 過濾機器人，再依 email 過濾測試帳號。問答環節確認了取得熱門賽事不需額外判斷 GameLive、設定與取得可共用相同 Route（不同 Method）、以及取消功能實作方式等設計決策。對 AI 開發而言，能明確知道這兩個功能的 API 規格、參數結構、以及過濾規則的實作位置與條件

## 關鍵業務規則

- - 熱門彩池賽事：設定熱門場中競猜賽事時，若該賽事資料已存在於資料庫中，必須先清空原有資料後再寫入新資料（即覆蓋式更新）
- 熱門彩池賽事：取得熱門場中競猜賽事時，「不需」判斷 GameLive 狀態，服務端返回什麼資料就回傳什麼，不做額外篩選
- Z 幣排行：過濾邏輯直接寫在既有的「取得錢包資訊」Domain Layer 函式中，不新建獨立函式
- Z 幣排行：機器人帳號使用 skipRobotUser() 函式過濾
- Z 幣排行：測試帳號透過使用者 email 是否包含「zbdigital」進行過濾（需人工確認：從清單來看，測試帳號 email 混用了 @zbdigital.net 與 @gmail.com，實際過濾關鍵字應以 @zbdigital 為準，但清單中多數為 gmail 結尾，過濾邏輯可能需再確認）

---

## 關鍵設計決策

- - 取得熱門彩池賽事不判斷 GameLive 狀態，由服務端全量返回，避免前端因狀態判斷不一致而遺漏賽事
- 設定與取得熱門賽事使用相同 Route 但不同 HTTP Method（POST vs GET），符合 RESTful 設計慣例且減少路由管理複雜度
- Z 幣排行直接修改現有 Domain Layer 函式而非新建函式，原因是減少重複程式碼與降低維護成本，所有錢包相關查詢都走同一入口
- 取消熱門彩池賽事的功能由既有「設定熱門場中競猜賽事」API 兼任，傳入賽事參數時若已存在則清空，不需額外開發取消 API

## 注意事項

- ⚠️ - ⚠️ 測試帳號過濾邏輯：文件設想區說 email 要核對「zbdigital」，但用戶交互設計的測試帳號清單中，多數 email 為 @gmail.com 結尾（例如 zbdigitaltest5@gmail.com），僅 robot001@zbdigital.net 與 robot002@zbdigital.net 為 @zbdigital.net。過濾條件應是「email 包含 zbdigital」而非特定域名，需人工確認過濾規則的正確關鍵字
- ⚠️ 文件問題區有一段被劃刪除線的內容（關於 PriceCenter route 路徑重複新增），標注「已修正」，表示這是歷史討論，不需再關注
- ⚠️ 取得熱門場中競猜賽事的 Response 範例包含大量 siteInfos 資料（超過 40 個站台），實作時需注意資料量對效能的影響，但文件未提及分頁或限制站台數量的設計
