## 摘要

本文件定義了從 Naver Sport 取得 KBO 賽事資訊的技術實作細節。賽前戰力分析與預測資料需以指定 key 寫入 otherinfo 欄位；賽中直播事件由 provider 合併 1~9 局後單筆送入 Kafka，最後由 parser 轉為 Markdown 格式寫檔。對 AI 開發而言，重點在於了解資料來源、API 格式、欄位對照與輸出規範，以便串接爬蟲、資料處理與即時資訊呈現。

---

## 關鍵業務規則

- - 戰力分析資料寫入 otherinfo 時須使用固定 key：win/lose（勝敗）、base（局數）、defense（平均自責分）、whip（WHIP）、vs_home 或 vs_away（對戰成績）。
- 投球類型資料需存放於 currentPitKindStats，並按 mapping：FAST→fastball（快速球）、SLID→slider（滑球）、FORK→forkball（指叉球）、CUTT→cutter（切球/卡特球）、TWOS→two seam fastball（二縫線速球）、CURV→curveball（曲球）、CHUP→changeup（變速球）。
- 關鍵球員統計使用固定 key：hra（打擊率）、hit（安打）、hr（全壘打）、rbi（打點）。
- 預測資料從 API 取得 selectionCount，直接以 (某隊人數 / 總人數) 計算比例後寫入 otherinfo。
- 直播事件中，若 relay 物件的 text 為空字串，代表為網站小標題，必須跳過不處理。
- 直播事件 text 內以 `<br/>` 分隔，輸出時須轉換為無序清單（Markdown bullet list）。
- 直播事件須由 provider 請求全部 1~9 局，將 2~9 局的 textrelays 集合附加至第 1 局清單後，才以單筆 Kafka 訊息送出。
- relay_data 需額外加入 relay_type key，用來區分 inning（局事件）與 HL（highlight），寫檔時據此分出不同標題。

---

## 關鍵設計決策

- - 選擇將 2~9 局事件合併至第 1 局後一次性發送 Kafka，是為了簡化下游消費邏輯，避免處理多筆分散訊息。
- 最終輸出採用 Markdown 格式（用 ## 做事件與 highlight 分隔，### 做局數，#### 做球員，列表使用 -），推測是便於前端直接渲染或存入內容管理系統。
