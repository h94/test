## 摘要

這份文件定義了 2025 年 6 月版本的三層系統架構：PRD Log/Gateway 層負責請求路由與日誌收集（NginxProxy → Gateway → Kafka → Loki 的整條鏈路）；賽事資料層說明爬蟲從 9/11/12/88 等站台抓取資料後，經由 CrawlerFlowService 或 CrawlerService 轉換為 ProcessedGameData，再透過 PriceCenterService、ClientFlowService 等分發給前端；InplayZ 層整合了預測、會員、商城、支付、社群等面向玩家的功能模組。對 AI 開發而言，這份文件提供了服務之間的資料流方向與觸發關係，可據此理解哪些服務有直接上下游依賴、哪些是平行的獨立模組。

## 關鍵設計決策

- - 靜態圖檔請求（如圖檔）不經 Gateway，由 NginxProxy 直接從 NFS 讀取後回傳，目的是減少 Gateway 的負載並加快靜態資源回傳速度
- Routing Info 不直接從 DB 讀取，而是透過 GatewayManager → GatewayAgent → Redis 的路徑快取在 Redis 中，讓 NginxGateway 能快速讀取路由配置以降低延遲
- Log 收集採用 Kafka 作為暫存層，再由 LogXService（處理 AccessLog）和 AppLogXService（處理 AppLog）分別寫入 Loki，實現日誌分離處理
- LogMonitor 檢查 Loki Log 後透過 MQService 發送告警到 Telegram，由 MQService 統一處理訊息派送而非直接呼叫 Telegram API
- CrawlerFlowService 將 GameData 轉換為 ProcessedGameData 後直接送到 Kafka 而非寫入 DB，目的是因 GameData 數量龐大，寫入 DB 會造成延遲，改為先送到 Kafka 讓下游消費者非同步處理
- CrawlerService 負責將 GameData 寫入 DB，但只處理賽事基本資料與賠率更新，不寫 Log，與 CrawlerFlowService 有明確分工
- GameCombineService 不使用 xxl-job 而是自行實作排程機制，因為排程需求經過優化調整，xxl-job 無法涵蓋所有場景
- Bet365Controller 負責從配置中找出該機器要運行的爬蟲，並透過 API 向 PriceCenterManager 取得爬蟲資訊與回報狀態，實現爬蟲任務的集中管理與狀態回報
- TeamLogoService 從 DB 取得 1xbet、leisu 等站台的隊伍 Logo 路徑後下載到 NFS，再由 WebpService 轉為 webp 格式，統一格式以利前端使用
- InplayZ 的 ZAgentService 部署在獨立機器（55.88）而非 PRD，推測為負責機器人預測、解鎖、灌分潤等背景任務，與主要服務分離部署以降低干擾

## 注意事項

- ⚠️ - ⚠️ 文件標題日期為 2025.06.01，但最後更新日期為 2025-06-05，可能有部分內容在 6/1 後被修改，需確認是否為最終版本
- ⚠️ GatewayManager 描述中「Ngix」應為「Nginx」的筆誤（「請求進到 Ngix 時從 Redis 中讀出配置」），可能導致對 NginxGateway 角色理解混淆
- ⚠️ 「InjuireService」可能為「InjureService」的筆誤（從功能描述「取得傷兵名單」推斷），對應到 injuriesapi 服務，需人工確認正確名稱
- ⚠️ 爬蟲 Providers 標註為「9,11,12,88 Crawlers Providers」，但數字意義未說明，可能為站台編號或機器編號，需人工確認
- ⚠️ InplayZ 架構中 PriceCenterSite、PriceClientSystem、ClientFlowService、PriceCenterService 重複出現在賽事資料架構與 InplayZ 架構中，暗示這些服務同時服務兩個系統，需要確認其操作邊界是否在兩個場景中有差異
- ⚠️ PredictRobot 與 ZAgentService 都提到「機器人預測」，需確認兩者的分工關係（PredictRobot 部署在 PRD，ZAgentService 部署在 55.88）
