## 摘要

本文件定义了预测机器人框架的核心架构与配置方式。开发者可了解机器人通过读取 predict_robot 表中的策略配置来决定投注目标，并每小时执行一次策略检查。文件中详细列出了 30 余种策略的具体触发逻辑，涉及赔率分析、伤兵名单、球队战绩、盘口变化及机器学习预测等维度。同时规范了下注记录的存储格式和管理 API，用于自动化投注和结果回溯。

---

## 關鍵業務規則

- - 机器人运行频率为每小时一次，依据各策略定义的 target 球种与联盟筛选赛事进行判断。
- 策略必须依据 predict_robot 表中的 enable 栏位（1为启用、0为停用）决定是否执行对应策略。
- repeat 栏位控制策略是一旦不符合条件就等待下一周期还是持续观察。
- 策略 1（随机下注）：随机决定是否对本周期比赛投注，若投注则随机选择独赢、让分或大小玩法一种。
- 策略 5（近况盘口差）：计算主客队近5场平均得分总和与大小盘口的差绝对值，若差距在3到6之间，且得分总和高于盘口则下注大分，反之小分。
- 策略 10（高胜率）：仅针对 NBA，若某队赛季胜率（pct）高于 0.65，则投注该队独赢或让分。
- 策略 11（实力相当盘口异动）：当让分盘口（HA）绝对值小于 3.5（表示实力接近），且两队赔率相减的绝对值大于 0.2 时触发投注。
- 策略 26（机器学习）：使用外部 ML 模型预测棒球或篮球的胜利队伍，仅下注独赢。
- 策略 27（MLB系列赛）：仅在系列赛第二场起触发，上一场赢球的队伍，其当场收盘球头若为正数则投注主队，反之投注客队。
- 策略 28（MLB系列赛）：第二场起，根据上一场相同对阵的比分输赢决定投注对象。
- 策略 29（MLB系列赛）：第二场起，判断主队为强队且其赛季胜率大于0.5时投注。
- 策略 32（MLB连赢/输）：第二场起，根据主队或客队连赢或连输的状态决定投注。
- 策略 33（MLB首场）：系列赛第一场，依据主队上一场比赛的输赢来决定本场投注对象，若赢则投主队，反之投客队。
- 策略 6-9（伤兵策略）：根据获取的伤兵名单，计算特定位置（控球后卫、中锋、得分后卫）的伤兵数量，投注伤兵数量较少的一方，玩法为让分或独赢。
- 下注日志必填项包含：策略ID、球种、日期、玩法、赛事ID、帐号、时间戳，以及触发策略的原始参数与结果。

## 關鍵設計決策

- - 使用 Cassandra 数据库存储策略配置与投注日志，设置较短的 gc_grace_seconds (60秒) 以优化写入性能。
- predict_robot 主键设计为单一的 strategy_id，意味着每个策略只有一个全局配置，无法做多条件分支。
- strategy_bet_log 使用 (strategy_id, game_type, date, mode, gid, account) 的复合聚类键，以高效查询特定策略在某天某场赛事的投注记录。
- 策略参数通过 DB target 栏位 (map<text, list<text>>) 动态配置，使得新增球种或联盟不需要修改代码。
- 投注 API 限制为一次只能下一注，因此框架必须循环或依次执行不同策略触发的多笔投注。

## 注意事項

- ⚠️ - ⚠️ 策略 5, 17, 18 等描述中提及的“所有球种”在 DB target 中仅配置了 SC, BS, BK, HL，开发时需确认是否后续有扩充。
- ⚠️ 策略 20 至 25, 27, 28, 29, 30, 31, 32, 33, 34 的“完成”栏位未标记为 V，可能仅为规划阶段或尚未实作完成。
- ⚠️ 策略 26 引用的机器学习 API 为内部 IP (192.168.9.231:22341)，供本地开发测试使用的 endpoint 可能在生产环境中不同，需人工确认。
- ⚠️ 文中'策略下注(判別特徵)'表格中存在多个没有 ID 的策略（如近五场分差、OVR>90、防御率等），这些可能是待讨论提案还是已弃案，状态不明确。
- 策略 11 中描述的 H A 盘口与赔率计算方式比较模糊，需根据实际原始数据格式验证。
