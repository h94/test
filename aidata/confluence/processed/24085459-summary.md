## 摘要

這份文件定義了 Payment 模組的前端頁面與 API 規格，包含儲值、訂閱、餘額查詢、交易紀錄查詢與方案取得六支 API 的路由、參數與回傳格式。對 AI 開發 paymentservice 最有幫助的是明確的 API contract：例如儲值與訂閱 API 採用 POST 並需傳入 AuthKey, Plan, Channel；查詢 API 採用 GET 並支援時間區間篩選；方案查詢 API 的回傳結構包含 Type, Name, Price, Value 與支付方式開關。同時 UI flow 提示了選擇方案 → 選擇付款方式 → 完成交易的互動流程，可輔助理解業務步驟。

---

## 關鍵業務規則

- - 取得全部方案 API 需回傳方案類型、名稱、價格、點數價值與可用支付方式（含啟用/停用狀態）
- 儲值/訂閱 API 必須傳入 AuthKey（會員驗證金鑰）、Plan（方案代碼）與 Channel（支付方式）
- 儲值紀錄查詢 API 回傳的 Status 欄位定義：1 = 成功，0 = 失敗，2 = 審核中
- 點數交易紀錄查詢 API 回傳欄位 Point 為消費點數，Price 為所需點數額度，兩者語意不同需區分

---

## 關鍵設計決策

- - 付款 API 重要性標為「低」，推測初期不獨立提供付款接口，而是由儲值/訂閱 API 整合付款流程
- 方案查詢 API 將方案類型分為 point（儲值點數）與月卡，透過 Type 欄位區分，而非設計兩支獨立 API
- 查詢 API 支援 starttime 與 endtime 區間篩選，表示交易紀錄查詢以時間範圍為主要篩選維度
- UI 設計明確區分儲值（點數）與訂閱（月卡）為兩個獨立流程，而非合併在單一畫面
