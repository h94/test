## 摘要

本文定義 OpenClawService 檢查隊伍合併資料（teams.tnamemap）錯誤的流程與業務規則。核心檢查兩個異常：隊伍被合併到明顯不同聯盟（如 MiLB 合到 MLB），以及同一隊伍在不同站台被合併成明顯不同的隊伍名稱。檢查結果寫入 Redis，只檢查主站台，足球球種因聯盟過多需指定 lid 查詢，附帶賽（Playoffs）視為正常案例不報錯。此功能定時每週一早上 8:30 執行。

---

## 關鍵業務規則

- - 隊伍合併檢查核心規則：league_name 與 tnamemap 中的 SiteLID 明顯不同（如 MiLB 被合到 MLB），視為合併錯誤（規則 4-1、3-3）。
- 團隊名稱明顯不同規則：team_name 與 tnamemap 中的 SiteTID 明顯不同，視為合併錯誤（規則 4-2、3-6）。
- 附帶賽例外規則：如果 lname 或 SiteLID 包含 'play off' 文字，則視為相同聯盟，不報錯（規則 4-3、3-8）。
- 只檢查主站台規則：合併檢查只過濾並檢查主站台的資料（規則 2-1 及站台代碼對照表），其他站台忽略。
- 足球球種查詢限制：足球球種聯盟過多，呼叫 GET /api/check-team/teams/{game_type} 必須帶 lid query 參數，否則回傳 400 錯誤。
- 合併資料欄位解析規則：tnamemap 中的 SiteLID 和 SiteTID 如為中英文，直接與 lname 和 tname 比對是否明顯不同；如為數字，則在同站內有多筆合併紀錄時，檢查是否有不同 SiteLID/SiteTID（規則 3-4、3-5、3-7）。
- 資料寫入規則：檢查出的異常資料格式與 GET teams API 回傳格式相同，但 tnamemap 只包含有問題的合併結果，透過 POST /api/check-team/wrong-teams-merge/{game_type} 寫入 Redis db3（55.80）。
- 定時執行規則：此檢查流程每週一早上 8:30 執行一次，並非即時觸發。

---

## 關鍵設計決策

- - 使用 Redis 暫存檢查結果（位置 55.80 db3），而非直接寫入資料庫，並透過 POST API 寫入，推測是為了讓後續潛在的 Web 後台讀取與過濾。
- 採用定時任務（每週一早上 8:30）而非即時檢查，降低系統負載，因為資料合併錯誤不必立即修正。
- 足球球種因聯盟數量過多，API 設計上強制要求指定 lid 查詢，避免單次請求資料量過大導致 timeout。
- 使用專屬 API 端點（/api/check-team/）將業務邏輯封裝在 OpenClawService 中，與主資料庫查詢解耦，符合微服務設計。
- 會議記錄提到白名單/過濾功能（Web 後台）暫緩開發，主因是龍蝦（OpenClawService）誤報率可能過高，導致人工過濾成本不划算，這決定了目前功能僅止於偵測與記錄，不具備自動排除機制。
