## 摘要

定義 PriceBackEndService 的商城商品 CRUD API 設計，包含新增、查詢全部、更新、刪除商品。該服務作為後台管理層，不直接操作資料庫，而是調用 ProductService 進行實際資料操作。關鍵業務邏輯：查詢時計算剩餘數量（remain_Quantity = initial_Quantity - 已提領數量）；新增/更新時驗證必填欄位、數值範圍與狀態枚舉；更新只能修改名稱、價格、數量、圖片；刪除前需確認商品存在。文件提供了詳細的時序圖、API 規格（路由、參數、回應範例）與多語系支援說明，對開發 PriceBackEndService 及與 ProductService 的對接有直接幫助。

---

## 關鍵業務規則

- - 商品名稱（語系：zh-TW）、類別、圖片路徑不得為空
- 商品價格（Price）必須大於 0
- 商品初始數量（Initial_Quantity）必須大於等於 1
- 商品狀態只能是「上架中」或「已停售」
- 更新商品時只能修改：名稱、價格、數量（推斷為初始數量）、圖片
- 查詢商品時，返回的 remain_Quantity 由 PriceBackEndService 計算：初始數量 - 已提領數量
- 新增和更新請求都需先通過 PriceBackEndService 的資料格式驗證，再轉發至 ProductService

---

## 關鍵設計決策

- - PriceBackEndService 不直接操作資料庫，所有商品資料的持久化由 ProductService 負責，PriceBackEndService 僅作格式驗證、業務邏輯（如剩餘數量計算）和轉發。
- 取得商品時，ProductService 回傳原始資料後，由 PriceBackEndService 計算並填充 remain_Quantity，而非由 ProductService 提供，保持計算邏輯在後台服務。
- 更新與刪除商品前，都先調用 ProductService 取得商品資訊以確認商品存在，避免對不存在的資源進行操作。
- 支援多語系商品名稱（PNames），儲存時使用語言代碼（如 zh-TW、en-US 等）的 key-value 結構。

---

## 注意事項

- ⚠️ - 刪除商品 API 的回應格式未定義，文件中的 Response 欄位空白，實作時需確認成功時的標準回應結構。
- 刪除 API 的路徑參數包含 {pclass}，可能表示同一商品類別下 PID 唯一，但其他操作未使用 pclass 作為路徑參數，命名與使用需注意一致性。
- 更新商品的 Request Body 中包含 PID，而新增時沒有，需確認 PID 是否由 ProductService 自動生成且不可修改。
- 文件中的欄位命名風格混用（小寫、駝峰、底線），例如 Request JSON 使用 PNames、PClass，Response JSON 使用 pNames、pClass，開發時需與實際 ProductService 接口對齊。
