## 摘要


本文件詳細定義了在 MemberService 新增新運彩水桶名單（newlottery_banned）完整 CRUD（5 支 API），以及擴充訊息中心 Notification API，使其支援 tid/enabled 過濾和硬刪除訊息的功能。作為 NewLotteryBackEndService 與 NewLotterySite 的統一資料來源，文件提供了具體的 API 規格（請求／回應格式）、Cassandra 存取規範、Redis 快取更新規則及實作步驟。對 AI 開發而言，可直接作為 API 開發與測試的依據，理解服務如何實現禁言檢核與通知系統的整合。

---

## 關鍵業務規則


- - CreateBanned 時 account 必須存在於 newlottery_users，否則回傳 HTTP 404。
- 同一 account 最多只能有一筆 active ban（endTime > 現在時間），重複新增時回傳 HTTP 400。
- endTime 格式固定為 yyyy-MM-dd HH:mm:ss，且為必填欄位。
- GET banned/{account} 只回傳 active（endTime > now）且 addTime 最大的那筆記錄；若無 active ban 則回 HTTP 404。
- DELETE banned/{account} 刪除該 account 中 addTime 最大的一筆記錄。
- CreateNotificationMessage 時 tid 必須存在於 topics 表中，否則回傳 HTTP 404。
- GET notification/messages 支援 tid query 過濾，只回傳指定主題的文章；GET notification/topics 支援 enabled query 過濾（0 或 1）。
- PUT notification/topics/{id} 可將 enabled 設為 0 來停用主題。
- DELETE notification/messages/{tid}/{id} 對 Cassandra 執行硬刪除，並同步清除 Redis 快取 key {tid}_{id}。
- Topic 與 Message 的 ID 均由 Service 端透過 PublicLibary.GenerateHashKey() 產生，客戶端不可自行帶入。

## 關鍵設計決策


- - 水桶功能複用既有 GameUserService.CreateBannedGameUser 的模式，但改以 account 為識別，並移除 Redis 快取，active 判斷完全由 endTime 與當前時間比較。
- 採用 Cassandra newlottery_banned 表（PK account, CK addtime）儲存歷史紀錄，使得多筆 ban 記錄可追溯，並以 addTime 最大值代表最新一筆。
- CreateBanned 時 userName 由 Service 查詢 newlottery_users 後自動帶入，前端 Request Body 不含此欄位，以確保資料一致性。
- Notification 的 messages 仍保留 Redis 快取，但於新增、更新、刪除後即時更新或清除快取，確保資料正確性。
- 選擇硬刪除訊息而非軟刪除，因為資料庫欄位中無 enabled 欄位，且後台需求為直接移除。
- 新增的 API 不需登入驗證（同既有 NewLottery API），由 BFF 層呼叫。
