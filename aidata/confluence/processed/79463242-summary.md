## 摘要

本文件定義至尊球王服務的完整技術設計，包括 Cassandra 資料表 (supreme_cycles、supreme_winners、supreme_records)、REST API 規格、時序圖與加權計分規則。系統可依球種/聯盟設定週期、權重與彩池，收集各類玩家活動資料（點數獲利、解鎖次數、文章互動、主推勝場、Z幣），結算後產生至尊球王獲得者。對 AI 開發而言，可直接依據此文件實作自動化資料同步、結算邏輯與 API 代理。

---

## 關鍵業務規則

- - 新增週期 (supreme_cycles) 時，cid 必須是目前已存在週期中最大的 cid 加 1，且不可與既有 cid 重複。
- 五項權重 (pointprofit_weighting、unlockcount_weighting、articles_likescommentscount_weighting、mainwincount_weighting、zcoinsprofit_weighting) 必須各自大於 0 且小於 1，總和必須為 1。
- 新增週期的 starttime 必須大於最新一個週期的 endtime；endtime 必須大於 starttime（單位為 timestamp 秒）。
- 更新週期時，若該週期已結算 (settlement == 1)，則不得更新 starttime、endtime 或權重。
- 更新 settlement 欄位時，若欲設為 1，該週期的 endtime 必須小於當前時間（⚠️ 原文敘述可能筆誤：『endtime小於現在的時間，settlement值不可為1』，邏輯與後端通常相反，需人工確認）。
- 呼叫 POST /supreme/records 設定活動資料時，只會寫入落在週期 starttime 與 endtime 之間的資料；data 欄位需為 JSON 序列化字串。
- 刪除至尊球王週期所有使用者活動資料 (DELETE /supreme/records/{gameType}/{lid}/{cid}) 前，需確認該週期存在且尚未結算。
- 新增至尊球王獲得者時，若各項原始值或分數未帶值，預設為 0。
- 更新週期彩池 id (PUT /supreme/cycles/.../bid) 時，bid 不可為空。

## 關鍵設計決策

- - 採用 Cassandra 資料庫，以 gameType 為 partition key，lid 與 cid 為 clustering key，可高效支援依球種與聯盟的查詢。
- 活動記錄表 (supreme_records) 使用 type + account 作為 clustering key，並將每日變動資料以日期為 key 存入 data map，便於增量更新與按日統計。
- 獲勝者表 (supreme_winners) 同時保留原始指標與百分比分數 (score)，結算時可直接使用加權總分，減少外部計算負擔。
- API 設計完全 RESTful，資源路徑直接對應 gameType/lid/cid，易於代理層轉發。
- 參考「殺手服務」的架構，開發至尊球王，保持一致的使用者體驗與操作邏輯。
- bid (彩池 id) 欄位標注為『未確定』，設計階段保留彈性。

## 注意事項

- ⚠️ - ⚠️ supreme_cycles 的 bid 欄位仍為未確定，實作時需先與業務確認。
- ⚠️ 更新 settlement 的規則中，『endtime小於現在的時間，settlement值不可為1』與一般結算邏輯衝突（通常應為 endtime < now 時才可結算），可能為文件筆誤，需人工確認。
- ⚠️ 至尊球王的『發文被按讚數與留言數』在 winners 表中合併為單一欄位，但 records 表的 ArticlesLikeAndComment data 包含 likecount、selfCommentCount、othersCommentCount，合併計算方式未明確定義，需人工確認。
- ⚠️ 數據類型 pointprofit 在 winners 表中為 int，但 records 中也可能出現較高數值，結算時範圍與溢位需注意。
