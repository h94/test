## 摘要

這份文件定義了 PriceCenterSite 如何透過 API 支援串關預測功能。對 AI 開發來說，重點在於理解新增的 POST API 及其嚴格的輸入限制（最少/最多關數、同場限制、每日上限），以及取得預測紀錄時，上鎖的 PG 預測必須隱藏特定欄位（將賠率等資訊設為空）。這些規則是開發預測相關 AI 模組時必須遵守的介面規範。

---

## 關鍵業務規則

- - 串關預測 API (POST predict/bets/PG/{authKey}) 最少需串兩關，最多串十關。
- 同一筆串關預測請求中，不能包含同一場比賽 (GID) 的多個預測項目。
- 每筆串關預測以預測標的中最晚的比賽時間為準，每位會員一天內最多只能有三筆預測。
- 請求參數 PredictBetDTO 新增必填屬性 GameType (賽事種類)。
- PredictBet 資料模型新增屬性 RollUpBets，用於儲存串關種類的賽事預測。
- PredictGame 資料模型新增屬性 PGPredictBets (List<PGPredictRecord>)，用於儲存上鎖的串關預測結果。
- 呼叫新增串關預測 API 時，若賠率錯誤，API 會回傳目前最新的賠率 (expiredBets)。
- 針對上鎖的 PG 預測，從 GET API 取得的 PGPredictBets 內容，其 Spread、OddType、WinLoss 需為空字串，Odd 需為 0。

---

## 關鍵設計決策

- - 區分成員和機器人介面：新增兩支 POST API，分別處理一般會員 (predict/bets/PG/{authKey}) 和機器人 (mechanic/predict/bets/pg/{account}) 的串關預測，以區分不同來源的請求。
- 賠率錯誤處理：當提交的賠率和當前賠率不符時，不是直接拒絕，而是回傳 expiredBets 讓前端可以顯示最新賠率供使用者重新確認，提升使用者體驗。
- 資料模型繼承：PGPredictRecord 繼承 GameBaseInfo，重複利用基礎賽事資訊，並加上 Mode, Spread, OddType 等預測專用欄位，確保資料結構的一致性。
- 屬性擴充：在原有 PredictBetDTO 和 PredictRecord 中新增 GameType 屬性，以支援跨球種的串關預測識別。

## 注意事項

- ⚠️ - 文件中部分 Request 和 Response 範例的欄位名稱大小寫不一致，例如 Request 為 'GID'，Response 為 'gid'，實作時需注意序列化設定需人工確認。
- Response 範例中 expiredBets[0].gDate 為 '2024-04-11'，與 Request 範例中的 '2024-04-10' 不同，提醒 expiredBets 可能會回傳不同日期的賽事賠率。
- API Parameter 中的 authKey 與 account 分別用於成員和機器人，透露出這兩類請求在驗證機制上的根本差異，開發時須注意權限控管。
