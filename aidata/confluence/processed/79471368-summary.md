## 摘要

文件記錄了一套以 AI Review Agent Server 為核心的自動化開發流程設計，包含強制使用 Plan 文件、自動檢查 Plan 規範與測試涵蓋率、自動化 Code Review、整合測試腳本生成、微服務地圖維護、DB/Redis 隱性知識顯性化、場景流程文件產生，以及 Confluence 文件轉換為 aidata 知識庫的架構。最後的 upgrade9 詳細定義了從 Confluence 擷取頁面、經 AI 摘要並分類索引的管線設計。

---

## 關鍵業務規則

- - Merge Request 必須帶有 Plan 才能執行，即使是小功能修改也須遵守
- PLAN 中必須強制要求單元測試及整合測試的對應 Code
- Plan commit 後需自動檢查是否符合 PLAN_SPEC.md 規範
- 於 Plan commit 時將「犯過的錯」結構化儲存為 lessons-learned，供 AI 後續寫 Plan 時自動對照避免重犯
- 將 DB 與 Redis 等資料源的隱性知識顯性化：當 DB schema 或 repo 更新時，自動分析並產生 db-detail.md 與 db.md，標記各欄位語意，並由資深工程師審核後搬運
- 新人工程師在 Plan 之前必須透過 AI 產出「任務理解文件」，由資深人員審核，確保對任務的正確理解（需在顯性化完成後才能執行）

---

## 關鍵設計決策

- - 選用 PLAN_SPEC.md 作為規範載體，驅動 Plan、Code、Test 的生成與檢查
- 透過 AI Review Agent Server 自動化流程，於 plan commit 後即時檢查並發送 Rocket 通知
- 在 Merge Request 階段，僅當 Plan 和 Code 相符時才產生整合測試腳本 (Bruno/Playwright)，並通知測試人員
- 建立微服務地圖 (服務索引檔與自述文件)，讓 AI 先行理解服務邊界，減少開發人員重複說明
- DB 隱性知識顯性化採用定期檢查 repo 與 schema 更新，並以 AI 對照所有 readme 來分析關聯，產出 db-detail 文件置於 _temps 資料夾，由資深人員審核後移動
- 場景流程文件 (Scenario Flow Document) 以業務流程為導向，描述系統流程、DB/Redis/Queue 使用、高風險行為與錯誤情境，用於協助 AI 及新人理解系統
- Upgrade9 設計使用 Confluence API 抓取特定頁面內容，以 markdown 形式暫存，再透過 AI 分析產生摘要與分類索引，最終形成 aidata 知識庫的分類文件結構
