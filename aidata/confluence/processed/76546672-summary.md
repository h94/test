## 摘要

本文定義了體育電子佈告欄（BulletinBoard）的技術設計，包含 Cassandra 主存儲與 Redis 快取的資料結構，以及完整的 CRUD API（新增、查詢單一/全部、更新、刪除公告）。重點在於多語系內容（map<text,text>）的儲存規則、公告方式（AnnouncementMethod）對欄位可見性的控制，以及快取查詢參數（cache=true/false）的資料來源切換機制。這份文件可以直接用來撰寫 API 的 Request/Response Schema、參數驗證邏輯與資料庫操作。

---

## 關鍵業務規則

- - 公告狀態 (status) 僅定義 0（未公告）與 1（公告中）兩種。
- 公告方式 (announcementmethod) 為 1（靠中）、2（靠右）、3（三個內容區塊）。
- 新增與更新公告時，maintopic 與 text1 為必填欄位（不可為空）。
- maintopic 的多語系 map 中，必須包含 zh-CN、en-US、zh-TW 三個 key，且值不得為空。
- text1、text2、text3 若有內容（非 null），其多語系 map 也必須包含 zh-CN、en-US、zh-TW 且值不得為空。
- 僅當 announcementmethod == 3 時，text2 和 text3 才允許有值；若為其他方式，這兩欄在新增與更新時需被忽略或清空。
- 更新公告時，若 text2 或 text3 未帶入或設為空值，則資料庫對應欄位會被清空（設為 null）。
- 更新公告時不可修改的欄位：aid、announcementmethod、addtime、sequence（若要修改 sequence，文件未提供規則，需人工確認）。
- sequence 欄位若未帶值，預設為 0。
- 查詢公告支援 cache 參數：true（預設）從 Redis 讀取，false 從 Cassandra 讀取。

## 關鍵設計決策

- - 採用 Cassandra 作為主要持久化儲存，Redis 作為快取層，以加速頻繁的公告查詢。
- 多語系內容使用 map<text,text> 儲存，key 為語系代碼（如 zh-TW），此設計允許彈性擴充支援的語言，但驗證邏輯強制要求特定語系不得為空。
- API 路徑統一前綴為 /advertisingservice/api/sport/bulletinboard/...，將此功能歸屬在廣告服務下的體育模組。
- aid（公告 ID）在新增時由後端系統自動生成，文件未揭露生成規則，需人工確認。
