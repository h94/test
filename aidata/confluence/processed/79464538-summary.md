## 摘要

本文定義了商務號會員系統與賽事 API 的技術設計，因商務會員機制與原有 GS 會員不同而獨立建構。核心包含：商務號登入需填入 businessCode、account、password，登入後生成 uid 供後續驗證，登入資訊保留 1 天且操作可續期；角色分 admin 與 trader，admin 可建立最多 3 個 trader 帳號、管理其啟停用與重置密碼，停用 trader 時會清除其登入資訊。提供 11 支 API 涵蓋登入、帳號 CRUD、訂閱資訊、賽事查詢等功能，時序圖揭示了 GameSettingSite → GameSettingService → Redis/Cassandra，以及取賽事時透過 PriceCenterService 的呼叫鏈路。對 AI 開發的幫助在於可據此建立商務會員的業務邏輯模型與 API 請求建構。

---

## 關鍵業務規則

- - 商務號登入必須傳入 businessCode（路徑參數）、account 與 password，成功後回傳含 uid 的登入資訊，uid 用於後續 API 請求驗證。
- 登入資訊保留 1 天，若期間有操作動作則持續延長效期。
- 商務會員角色分為 admin 與 trader，每個商務號只能有一個 admin，但 admin 最多可建立 3 個 trader 帳號。
- admin 可以管理所有 trader 的啟用/停用狀態，並可直接重置任何 trader 的密碼；trader 僅能修改自己的密碼。
- 當 admin 將某 trader 帳號停用時，系統必須一併刪除該 trader 的所有登入資訊（Redis 中的 session）。
- 所有商務 API 都需要透過查詢參數 uid 進行身份驗證，只有 admin 可以呼叫「取得商務所有帳號」與「更新商務帳號狀態」這類管理端點。

---

## 關鍵設計決策

- - 因商務號會員機制與原有 GS 會員系統不同，決定另建獨立的商務會員 API，不沿用舊的會員服務，避免相容性問題。
- 採用 Redis 快取登入資訊，並藉由每次請求續期來管理 session 逾時，而非固定時間強制登出。
- 會員權限控制直接在 GameSettingSite 層驗證角色，管理型 API（如取得所有帳號、更新狀態）僅開放給 admin 角色調用。
- 賽事資料查詢路徑為：GameSettingSite → PriceCenterService → Cassandra，將賽事查詢邏輯分離至 PriceCenterService，維持 GameSettingService 專注於帳號與權限管理。
