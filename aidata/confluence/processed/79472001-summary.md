## 摘要


本文為 NewLotteryBackEndService 討論區管理功能的技術設計文件，定義了後台五支 BFF API（看板列表、主題/回文分頁、審核等），並明確規定所有討論區資料與業務邏輯必須透過 RestfulClient 轉接 communityservice，嚴禁直連 MeiliSearch 或 Cassandra。文中詳細說明了 API 的 I/O 規格、請求參數、回應欄位與錯誤處理，以及 provider/service/controller 的分層實作步驟。對 AI 開發者來說，這份文件提供了可直接對照的 API 契約、架構硬規則，以及與 communityservice 後台 API 的整合架構。

---

## 關鍵業務規則


- - communityservice 是討論區資料的唯一 owner，BFF 只做透傳，不實作討論區業務邏輯。
- 後台列表需回傳完整 account，BFF 對外永不回傳 user（authkey）。
- status 欄位：1=公開、0=隱藏；刪除為物理刪除（由 communityservice 執行）。
- 審核行動：hide 對應 status=0，restore 對應 status=1，delete 為物理刪除。
- BFF 本地驗證：targetType=comment 時必須提供 commentId，否則回傳 400；非法 action/targetType 亦回傳 400。

---

## 關鍵設計決策


- - 禁止直連 MeiliSearch 和 Cassandra，唯一資料路徑為 RestfulClient → communityservice，以確保資料一致性和邊界清晰。
- 對 tools 暴露的 BFF API 不需要管理員 authKey/Token，沿用現有後台 API 慣例。
- communityservice 另開 ticket 實現後台 API，本 ticket 以契約先行開發 BFF，待下游就緒後整合驗收。
- 採用 POST /api/forums/moderate 單一端點處理 hide/restore/delete，而非分散多個 API。
- 實作分為 Provider、Controller I/O 定義、Service 邏輯、整合測試等階段，Phase 2 I/O review 通過才進入實作。
- 若下游分頁僅提供 next_page，BFF 需在 Service 層轉換為 page+total，或與前端約定游標分頁（待確認）。
