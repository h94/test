### 操作紀錄 /log

**路由**：`/log`  
**對應 API**：  
- `GET /api/v1/logs?date=...&gameType=...` → 取得操作記錄（由 `GetLogAction` 封裝）  

**這個頁面能做什麼**：

**功能限制**：  
| 限制條件 | 使用者看到的行為 |

**狀態說明**：

### 人工合併賽事 /mergegame

**路由**：`/mergegame`  
**對應 API**：  
- `GET /api/v1/sitegames` → 取得站台原始賽事列表  
- `POST /api/v1/sitegames/merge` → 提交合併請求（合併原始賽事）  
- `POST /api/v1/games/merge` → 提交賽事合併（針對已合併的比賽）  

**這個頁面能做什麼**：  
- 搜尋指定球種、時間範圍的賽事  
- 切換「強制合併賽事」模式（僅顯示已合併比賽）  
- 勾選要合併的對象（可分為「主」、「合併」、「交換」三種角色）  
- 執行合併操作  
- 查看某筆賽事的合併資訊與已合併的站台賽事  
- 進階篩選（顯示欄位、停用特定站台）與聯盟篩選  

**功能限制**：  
| 限制條件 | 使用者看到的行為 |  
|---------|---------------|  
| 同一站台的原始賽事已選為「主」時 | 該站台的其他原始賽事 checkbox 變灰禁用（除非已經在「合併」列表中） |  
| 「交換」勾選框 | 當該賽事已有 gid（已合併）或 站台已被選為主且未在合併列表中時，checkbox 禁用 |  
| 搜尋時未選擇日期 | 預設使用當天日期區間，但仍可搜尋 |  

**狀態說明**：  
| 資料狀態 | 前端顯示行為 |  
|---------|------------|  
| `status` 欄位 | 以 `StatusMap` 對應顯示中文狀態文字 |  
| 賽事已有 gid（已合併）| 「合併資訊」欄顯示合併數量，點擊可展開查看詳情 |  
| 強制合併模式開啟 | 僅顯示已合併的賽事 |  

**錯誤處理**：  
| 錯誤情境 | 使用者看到的行為 |  
|---------|---------------|  
| 搜尋 API 失敗 | 顯示「資料取得錯誤」提示 |  
| 合併 API 失敗 | 顯示「合併失敗」與後端訊息 |

## 跨頁面的共用規則

- **登入驗證**：所有路由（除 `/login`）都需登入，由 router `beforeEach` 守衛檢查 cookie `user`。未登入自動導向 `/login`。  
- **時間格式**：多數使用 `Date.convert(value).format("yyyy-MM-dd hh:mm")` 或 `"yyyy-MM-dd hh:mm:ss"`。日期輸入使用 `<input type="date">` 和 `<input type="datetime-local">`。  
- **狀態對應文字**：  
  - 賽事狀態：透過 `GameStatusSelect`（config/game/GameType）或 `StatusMap` 顯示中文（例如 1→進行中，2→已結束）。  
  - 操作行為／影響範圍：由 `ActionMap` 與 `ScopeMap` 轉換。  
- **錯誤提示**：  
  - 短暫提示：使用 `SetHint(title, message, type)` 在右上角顯示 3 秒。  
  - 永久錯誤記錄：使用 `AddErrorMsg` 將錯誤加入全局清單，可透過 `ErrorButton` 組件查看。  
- **全域 Loading**：任何 API 呼叫前後會調用 `SetLoading(true/false)` 顯示遮罩。  
- **篩選條件**：多數搜尋欄位為自由文字部分匹配（不區分大小寫）。  
- **表格操作**：多數頁面支援點擊表頭排序（部分欄位）。  
- **連結支援**：許多頁面提供跳轉至編輯原始資料或相關頁面的小圖示。

## 權限控制邏輯

- 僅需登入即可使用所有功能，前端無角色權限區分。  
- 後端 API 仍會進行權限驗證（需人工確認），前端只負責隱藏未登入狀態下的頁面。  
- 登入狀態透過 cookie `user` 判斷，登出時清除該 cookie 並導向 `/login`。

## 常見錯誤（此前端專屬）

- ❌ 時間格式不統一：部分頁面使用 `datetime-local` 拆分日期與時間選擇器，容易造成使用者輸入混淆 → 應統一使用 datetime-local 或明確標示。  
- ❌ 部分頁面搜尋按鈕在未載入必要條件時仍可點擊，導致無效請求 → 應加上 disabled 狀態。  
- ❌ 狀態文字對應表分散在多個 config 檔案 → 建議集中管理，避免不一致。  
- ❌ 大量資料表格未提供分頁，僅有 scroll 加載，可能效能不佳 → 建議考慮虛擬滾動或分頁。  
- ❌ 部分 API 錯誤僅 console.error，未給使用者明確提示 → 應補上 SetHint 或 AddErrorMsg。  
- ❌ 日期控制按鈕（增加/減少小時）直接修改前端狀態，與搜尋條件未同步儲存 → 可能導致使用者誤以為查詢已完成。
